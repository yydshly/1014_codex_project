## 1. 本质

EdgeChat 同时包含 Vue 前端、Workers / Hono 后端、数据结构、权限、实时通信和部署流程。部署者在自己的 Cloudflare 账号下准备资源，成员使用账号登录。首先应把它作为一套完整应用理解，再按需要做二次开发。

自部署对应实例与资源的归属；无需维护常驻服务器对应平台托管底层运行。账号、密钥、更新、备份和实际用量仍有运营责任，不能由 Serverless 推导出无限免费或无限容量。

## 2. 能力和边界

| 能力 | 主要依据 | 边界 |
| --- | --- | --- |
| 群聊与私信、回复、提及、置顶 | ChannelRoom、消息提交和数据层 | 实际会话成员与访问权限；DM 检查拉黑 |
| 图片、文件和录音消息 | 上传与附件实现 | 默认上传上限 20 MiB；录音消息与实时通话不同 |
| 网页一对一语音 | voice-calls 协议 | 不包括群语音、视频、SFU 和 Android 通话；TURN 需配置 |
| Telegram 双向桥接 | Bot API 出站、Webhook 入站 | 群映射需配置；私信不参与；媒体大小/类型受限 |
| 两实例群绑定 | instance-bridge-v1 协议 | 绑定后的本站原创无附件新消息，不补历史 |
| 邀请、权限、封禁 | README、RBAC、管理员初始化 | 管理权限与会话成员权限分开，无默认管理员密码 |
| 网页、PWA、Android、TG 提醒 | README、通知运行规则 | Android 不承诺停止后即时通知；TG 提醒有预算、不含正文 |
| WebMCP | frontend/src/webmcp.ts | 五个入口，依赖兼容客户端和外部 AI |

## 3. 架构

```text
浏览器 / Android Web UI / 兼容 AI 入口
                   │
            Workers + Hono
          登录、授权、业务接口
             │           │
      Durable Objects    │ 直接访问存储
      房间/收件箱/任务    │
             └─────┬─────┘
               D1 / KV / R2
             数据 / 会话 / 文件
```

这是职责关系，不是每条请求的固定调用顺序。

- Vue 呈现界面与交互；服务端仍需独立授权。
- Workers 处理请求、身份、权限、文件读写入口和第三方回调。
- ChannelRoom DO 管理房间连接、消息提交与广播；UserInbox 处理用户级推送，其他 DO 协调通话、桥接和通知任务。
- D1 保存业务关系、消息和跨实例 outbox；KV 的 SESSIONS 绑定保存登录会话；R2 保存附件字节。
- WebSocket 负责实时通知；历史消息仍需要持久存储与重新同步。

## 4. 四条业务链路

### 文字消息

前端请求 → 身份与会话授权 → 处理回复、提及、拉黑与重试标识 → 加密正文并写入 D1 → 房间广播 → 异步未读和桥接任务。

先保存后广播。断线恢复需要 HTTP 同步。clientMessageId 用于同一消息重试去重。跨实例 outbox 与消息通过 D1 事务/触发器一起登记，后续异步投递；Telegram 出站尽力转发不能视为同等持久重试保障。

### 附件

上传校验 → 加密字节写入 R2 → 发消息携带引用 → 核验附件可用性 → 保存广播 → 接收者验权下载，由 Worker 解密。

上传完成和消息发送是两个步骤。文件引用、存储字节与访问权限需要一起理解。

### Telegram 回流

Webhook 验证 Secret → 查询群映射 → 解析外部身份 → 来源消息去重 → 媒体按规则导入 → 本站保存并广播。

入站源码对超过 16 MB 的附件提示未同步。来自其他桥的消息不再进入出站桥接，避免循环转发。

### 网页语音

呼叫 → 验证 DM 双方、有效状态与拉黑关系 → Inbox 来电 → 交换 SDP/ICE → WebRTC 直连或已配置 TURN 中继 → 挂断/超时释放。

Worker / VoiceCall DO 不转发或保存音频；WebRTC 承担音频传输。双方需在线并留在聊天工作区；没有 TURN 配置时不能把直连失败解释成中继已成功。文档中的单次通话上限为 1 小时；后台与锁屏表现待真实设备测试。

## 5. 两种桥接

| 维度 | Telegram | 跨 EdgeChat 实例 |
| --- | --- | --- |
| 机制 | Bot API / Webhook | 签名 HTTPS 请求 |
| 建立 | Bot 配置与群映射 | 一次性邀请，双方管理员确认 |
| 内容 | 文字与多种媒体，有格式和大小限制 | 本站原创无附件新消息 |
| 恢复 | 出站尽力转发 | 持久 outbox、重试、接收去重 |
| 共同边界 | 群组范围，其他桥导入的消息不继续跨桥传播 | 同左 |

跨实例协议：每群最多一个未撤销绑定；邀请 10 分钟有效；不补历史，不传播跨站编辑和撤回。对方收到的副本不会随本站删除消失，投递不承诺来源发送顺序。

## 6. 加密信任模型

新正文和新附件使用 AES-256-GCM 服务端静态加密。32 字节密钥与随机 nonce 配合认证上下文：正文绑定会话/发送者，附件绑定对象键。密文带 key ID，轮换后仍可选旧密钥读取。

Worker 在写入前接触明文，读取时验权后解密，部署方和 Cloudflare 运行环境仍需要被信任。历史明文不自动回填；元数据不代表全部加密；后台无正文查看入口不等于部署者技术上无法读取。此模型不能称作端到端加密。

## 7. AI 的位置

源码注册 edgechat.login、edgechat.list_channels、edgechat.read_messages、edgechat.send_message、edgechat.open_dm 五个工具，复用现有会话和业务 API，发送工具当前用于纯文字。

外部兼容 AI 可操作这些入口。模型、推理、摘要、自动回复由外部系统实现；WebMCP 工具注册不能作为这些智能行为已经内置的证明。

## 8. 意义与取舍（研究判断）

1. 托管基础设施降低机器维护负担，但运营、备份、密钥和平台依赖仍存在。
2. 桥接降低迁移聊天入口的阻力，同时引入外部副本、同步范围与投递一致性问题。
3. WebMCP 展示将现有应用变成 AI 工具的一种路径，明确授权与动作范围仍是基础。
4. 小团队、私人圈子和 Telegram 社区值得进一步试部署；严格隐私需求要先核对信任模型；大规模和企业场景需要具体需求与实测。

## 9. 共同理解与产品判断（研究判断）

以下整理后续讨论形成的理解与取舍。上游功能事实仍以固定版本为准；扩展方案和价值排序属于研究判断，尚未通过实际用户、部署或付费验证。

### 9.1 三层理解：通信、入口、互联

| 层次 | 当前实现与含义 | 边界 |
| --- | --- | --- |
| 基础通信 | 文字群聊、单聊、回复、文件与图片、录音语音消息，以及网页一对一语音通话 | 语音消息与实时通话不同；群语音、视频会议和 Android 通话不在当前通话范围内 |
| 使用入口 | 网页、PWA、Android 客户端 | 多端入口不等于向任意网站提供现成嵌入组件 |
| 外部互联 | Telegram 群桥接、EdgeChat 实例互联、API / WebMCP | 其他平台需要适配；AI 的模型、任务和执行能力由外部系统提供 |

因此，它既实现聊天本身，也实现围绕聊天的多端访问和跨系统互通。将其称为“聊天能力的库”容易低估其完整应用属性；将其称为“通用接入模块”又容易高估现成封装程度。

### 9.2 能否变成网页里的聊天模块

可以在其通信后端基础上继续开发网页浮窗、页面讨论区、站内私信或客服入口，但这仍是一项二次开发工作。

| 需要补充的部分 | 具体工作 |
| --- | --- |
| 嵌入界面 | 将完整工作区封装为小组件，处理样式隔离、移动布局、未读提醒和宿主页面交互 |
| 网站身份与权限 | 对接网站账号和登录状态，明确用户可以进入、读取和发送哪些会话 |
| 业务对象与会话映射 | 为页面、项目、订单或问题建立对应会话，处理创建、加入、关闭与历史访问 |
| 接口封装与稳定性 | 封装消息收发、附件、连接恢复、错误处理和接口版本，支持需要的前端技术栈 |
| 后端运行 | 部署通信、存储与文件资源，持续处理运维、配额、备份和密钥 |

嵌入的是界面，身份检查、权限、存储和实时转发仍由后端承担。已有 API 也不等于已提供面向第三方网站的成熟聊天 SDK。

### 9.3 六类扩展方向：可开发不代表值得产品化

| 方向 | 可能解决的问题 | 还需要补什么 | 当前判断 |
| --- | --- | --- | --- |
| 客户交付协作室 | 客户与交付团队围绕一个项目讨论、改稿、传文件和确认交付 | 文件版本、任务、交付确认、客户与项目权限 | 沟通有明确业务对象，可优先访谈需求；尚未证明商业机会 |
| 页面反馈与处理模块 | 用户在出问题的页面反馈，开发者获取上下文并跟踪解决 | 页面上下文、问题状态、负责人、通知、嵌入与账号对接 | 可先在已有项目验证；若无需实时沟通，表单加状态也可能足够 |
| Telegram 社区支持台 | 群内求助得到归档、分配和跟进 | 问题归档、负责人、状态、最终答案回流 | 与现有桥接特色相符，但目标人群较窄 |
| AI 任务协作室 | 人和 AI 围绕任务交流，执行后回传结果 | 模型、上下文、工具执行、状态、人工确认和失败恢复 | 需要形成办事闭环；仅接入对话模型不足以证明价值 |
| 通用嵌入聊天 SDK | 其他网站和软件便捷接入聊天 | 多框架组件、账号整合、稳定接口、多租户、文档和运维 | 自用可有工程价值；独立销售需找出特别优势 |
| 多人音视频 | 群语音、视频会议、屏幕共享 | 多人媒体传输、会话管理、网络质量、移动端和运维 | 与当前一对一语音相比改造较大，暂不优先 |

这些方向是从技术基础推导的候选方案。它们不能登记为上游已实现功能，也不能用来证明用户需求或付费意愿。

### 9.4 成熟产品如何影响价值判断

可用来比较的成熟产品包括：提供网页客服、AI 和多渠道支持的 [Chatwoot](https://www.chatwoot.com/features)，提供聊天 SDK 与界面组件的 [CometChat](https://www.cometchat.com/chat-and-messaging)，以及提供反馈收集、讨论和进展跟踪的 [Canny](https://canny.io/features/portal)。这些官方产品页是产品比较参考，不属于前述 18 个固定版本上游文件。

由这些现有选择推导出的研究判断是：群聊、私信、文件、语音、网页挂件或 AI 接入本身，通常不足以成为一个新通用聊天产品的独特优势。围绕客服、项目或反馈继续开发，也需要先发现现有产品未充分满足的具体需求，而不能仅凭“可以扩展”就判定值得投入。

这个库仍有三类实际价值：

1. **直接使用**：需要在自己的 Cloudflare 账号下部署，并与 Telegram 群互通的独立聊天室。
2. **工程复用**：已有明确业务需求，且需要修改通信逻辑、会话模型或接入方式时，减少部分基础开发工作；实际节省多少仍需评估。
3. **研究学习**：观察实时通信、权限、存储、桥接与 AI 操作入口如何组成完整应用。

### 9.5 当前阶段的取舍

本轮共同判断是：**保留原理整理和源码分析，暂不主动继续开发通用聊天模块或新产品。** 等某个真实项目出现明确通信需求后，再比较 EdgeChat、成熟产品和更轻量的实现方式，按需求、改造量、许可条件与运行成本选择。

这个判断针对当前缺少明确需求的阶段，不是永久否定项目价值，也不改变本研究项目的维护状态。后续需求和实测证据出现时，应重新评估。
