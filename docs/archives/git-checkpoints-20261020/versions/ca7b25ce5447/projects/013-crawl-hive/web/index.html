01 / SOURCE CONTROL

来源控制：先决定去哪里看。

来源决定信息能否进入系统。用户选择来源类型和目标，系统在这个范围内周期运行；目前一个任务对应一种来源。

对应价值

把关注范围交给用户控制，减少无关来源，让每条信息的来历更清楚。

固定版本已有的 4 类监控来源；手机上可横向滑动表格
来源用户指定什么实际获取方式覆盖边界
X社交帖子@账号、查询词、关键词Grok 的 x_search 搜索需要 API 密钥；结果不等于完整订阅信息流
Telegram公开频道公开频道名称或链接频道网页预览 t.me/s只读公开预览；不读私有群或全部历史
公开网页官网／博客／文档具体 URL取 HTML，比较新增文本行不执行 JS、不递归全站；保存前 12,000 字符用于比较
DexScreener代币与交易对链、数据流、关键词或观察地址档案、推广、搜索与行情接口依赖第三方覆盖，不是完整链上索引器
获取范围

账号、频道与 URL 由用户给定

Telegram 和网页不会根据关键词替你寻找更多频道和网站。X 可以按查询词搜索；代币来源还会读取预设的新币数据流。

补充检查数据

RPC 与 GeckoTerminal 有不同角色

Solana／EVM RPC 和 GeckoTerminal 用于代币扫描中的链上状态、持币、合约或市场检查，不应算成新的通用信息平台。

建议新增

RSS、GitHub 仍属于改造方向

原项目没有独立的 RSS 或 GitHub 适配器。监控某个网页 URL，也不等于支持该平台的完整 API。

源码依据：任务与来源模型、X、Telegram、网页、DexScreener 来源、补充扫描数据。

02 / SEARCH & COLLECTION

信息搜索：主动找，或持续盯住。

搜索尝试找到相关内容；轮询则反复观察指定目标，等它出现更新。这个库同时使用两种获取方式。

对应价值

让系统按周期获取新内容，减少用户重复检索和反复打开页面的操作。

SEARCH / 主动检索

给出查询条件，向来源找

X 将账号、查询文字和时间条件交给 Grok；DexScreener 的 search 数据流按关键词查交易对。

WATCH / 指定目标轮询

给定目标，读取新变化

Telegram 按消息编号读取；网页先保存基线再比较新增文本；档案与推广列表也会定期拉取。

A

X：账号限制＋查询文字＋时间条件

@ 开头的目标变成账号限制，其他目标作为查询词，与关键词合并，用竖线拼成 Search for 提示文字。账号和起始日期另外传入搜索工具，模型据此检索并提取候选。

账号：@示例账号
Search for：查询词 | 关键词一 | 关键词二
时间：只考虑上次记录时间之后的帖子

竖线是提示文字；程序没有自行解析严格 AND／OR 查询，也没有逐条硬查原帖必须包含哪个词。

B

Telegram：先取指定频道的新消息

读取公开预览，以消息编号记住进度。首次只取最近 5 条，以后取编号更大的消息，再交给规则或 AI。关键词不会扩大频道范围。

指定公开频道 → 取消息 → 对比上次消息编号
新消息 → 进入规则或 AI 处理

网页：先建基线，再找新增文本

第一次记住页面，不产生更新候选。以后读取 HTML、去掉脚本与样式，与上次文本比较，把新增行合成一批，再检查关键词与可选摘要。

第一次：记住指定 URL 的文本
下一次：取页面 → 找新增行 → 关键词检查
只有删除、没有新增行时，不产生更新候选

D

DexScreener：列表发现、词搜索与地址观察

profiles 拉新币档案，boosts 拉推广列表；search 对前 5 个关键词分别搜索。普通新币路径再按流动性、交易量、估值和年龄筛选；指定观察地址走成交量变化分支。

展开：搜索与混合数据流的实现例外

只要 feeds 包含 search，合并后的普通候选都跳过包含词硬检查，包括同时来自 profiles／boosts 的候选；排除词仍检查。观察地址的分支还绕过适配器这一处的关键词与普通行情阈值，后续共享流程仍会处理候选。

周期与进度也是获取的一部分

任务用消息编号、上次时间或页面基线记住进度，受并发、预算、失败退避和后台在线状态影响。“持续”不代表全量、实时或永不漏报。

依据：调度器、搜索与 AI 预算。

03 / FILTERING & KEYWORDS

信息过滤：搜索词、硬规则和 AI 偏好。

关键词可能用于发起搜索、直接丢弃文本，也可能成为模型判断相关性的参考。三种作用需要分开理解。

对应价值

让留下的信息更接近关注点，同时看得见过滤依据和可能漏掉内容的位置。

FIND

搜索词

决定向来源尝试找什么。用于 X 查询文字与 DexScreener search。

MATCH

程序硬规则

按文本是否含词决定通过或过滤，可以明确解释命中了哪个词。

INTERPRET

AI 偏好

请模型判断相关性。结果可能没有字面包含关键词，但被模型认为相关。

不同来源中，关键词的实际作用位置
来源／模式什么时候生效需要理解的例外
X进入查询文字与 AI 偏好没有逐条硬查原帖必须含包含词
Telegram，无 AI对消息原文做包含／排除检查通过后还要求 $币代码或合约地址
Telegram，有 AI将词表和消息交给 Grok没有先逐条执行相同硬过滤；一次最多前 40 条、每条前 800 字符参与提取
公开网页对整批新增文本硬检查，然后才可选 AI 摘要一行含排除词，整批更新可能跳过；不逐行独立筛选，也不强制币名
DexScreener用于搜索，或匹配名称、代码和描述search 和观察地址存在上一节说明的绕过条件
共享匹配函数的确定规则

忽略大小写，直接做子串匹配；包含词任意一个命中即可，包含词为空则不限制；任意排除词命中优先过滤。没有分词、整词、同义词、正则或 AND 条件。

可编辑规则示例

改几个词，看这一步为何通过或过滤。

仅模拟共享关键词函数，不执行搜索、AI 或后续代币检查。

清空包含词可查看“不要求包含词”的结果。仅这一步通过，仍不代表最终会产生提醒。

最终还会检查什么？

finalize 再检查候选类别、最低置信度，以及“摘要＋币代码”里的排除词；不会重新硬查包含词，也不是重新检查完整原文。如果 AI 摘要遗漏了原文中的排除词，最终检查不能保证识别出来。

依据：matchesKeywords、AI 提取与 finalize、词表规范化、网页先过滤后摘要。

04 / PROCESSING & PRESENTATION

信息呈现：从候选，变成带来源的提醒。

呈现之前，还有结构化、条件检查、身份关联、去重与可选分析。用户看到的是处理后的信号，并非全部采集内容。

对应价值

让用户知道发生了什么，能回到原文核实，并在之后判断提醒是否有用。

  1. 01

    提取候选字段

    摘要、信号类型、置信度、来源 URL，以及可选币名／地址。模型输出 JSON，规则路径则按固定逻辑构造候选。

  2. 02

    检查条件，关联代币并去重

    检查类别、置信度和排除词，尝试关联交易对并记录价格。按任务自己的“代币＋信号类型”在 12 小时内抑制重复；无代币时有其他候选键回退。

  3. 03

    可选 AI 分流与风险检查

    Jev 可按关注价值分流；支持范围内的代币进入安全检查。DANGER 过滤，预算不足延后；扫描连续第二次失败会放行无判定信号。

  4. 04

    保存信号，按归属交付

    保存摘要、引用、时间、归属和判定等。当前持久化以信号与状态快照为主，不能理解为所有原始消息都被完整归档。

  5. 05

    追踪后续，形成反馈

    关联代币的信号按窗口和涨幅目标追踪；无代币可处于未计分状态。普通信息的“有用／无关”和进展评价，需要通用化时另设标准。

原作已有信号和引用的交付。跨平台同一事件合并、完整原文快照、提醒触发理由、每日摘要和普通用户反馈，仍需作为通用化建议单独实现，不能把本页示意当作已有能力。

依据：候选处理、信号字段、去重与结果状态、持久化、Telegram、MCP。

四个环节，围绕同一条主线

控制范围 → 持续获取 → 按规则筛选 → 交付可追溯的信号。历史和变化识别贯穿其中；具体价值需要真实任务与反馈验证。

“爬虫蜂群”是产品表达。真正需要理解的是：谁定义目标、怎样获取信息、何时值得打断用户。

L1

信息监控内核

来源、调度、增量、规则、摘要、通知。这里最值得迁移到其他场景。

迷因币是什么？

由网络梗、社区或热点带动的加密代币。关注度变化是原项目选择监控社交信息的背景。

一个 crawler 是什么？

一个带来源、目标、规则和运行周期的任务。当前每个任务只有一种来源；同主题多来源需要新增组织层。

“蜂群”怎么协作？

任务共用服务、扫描和展示。没有从源码中看到任务节点彼此协商的去中心化网络。

依据：核心模型、调度器、处理流程。分层是本研究对结构的归纳。

01 / COVERAGE

少开几个页面

把来源放在一个地方，按周期持续观察。价值取决于来源是否覆盖你真正关心的地方。

02 / RELEVANCE

少读无关内容

关键词与自然语言偏好帮助筛选。需要同时关注误报与漏报，模型置信度不能替代实际评估。

03 / CONTEXT

知道变化意味着什么

把摘要与领域检查放在一起。原项目以代币和行情串联；通用事件关联仍需新建。

04 / FEEDBACK

回看这次提醒有用吗

保留来源、时间和后续结果。币价规则便于计分，其他场景需要各自定义“有用”。

与已有信息获取方式的差异：研究判断，非产品性能实测
方式适合解决仍需要你做什么
直接搜索带着明确问题，找某个时间点的信息反复检索、比较新旧、判断是否有新进展
RSS / 聚合阅读稳定订阅已提供信息流的来源设置来源，阅读与筛选，处理同一事件的重复报道
网页变化提醒跟踪一个具体页面的文本变化区分布局噪声和实际变化，补足跨来源上下文
CrawlHive 的方法持续采集＋按偏好解释＋领域检查＋通知挑选好来源、校准规则、核实结果和实际效果
✳

最值得验证的假设

在相同来源范围内，能否减少无关提醒，同时更早发现用户认为有用的变化？需要用真实任务、人工标注和长期日志验证。仓库本身不能证明这一点。

延伸 05 / SYSTEM ANATOMY

一个应用，串起多种外部服务。

代码结构较集中，适合观察完整流程。长期监控还需要处理进程重启、持久化、限流和来源变化。

运行边界

后台必须持续在线

应用进程停止，定时监控就停止。静态 GitHub Pages 可以展示本研究网页，原监控系统本身需要服务端与密钥配置。

规模边界

先解决可恢复，再扩大并发

文件快照和进程状态适合轻量验证；多人、多实例或大量任务时，需要共享存储、任务协调、投递记录与恢复机制。

技术词汇展开：RPC、MCP、游标、去重、置信度分别是什么？
RPC
向区块链节点询问状态的接口。通用版可随链上模块一起移除。
MCP
让助手调用应用工具的协议。协议连接成功与具体客户端兼容仍需分别验证。
游标
记住读到哪里，例如消息编号、上次运行时间或页面摘要，减少重复采集。
去重
判断两条记录是否重复。相同主题可能有不同进展，不能仅按主题全部抑制。
置信度
规则或模型给出的判断分值。未经校准时不能直接视为事实正确概率。
事件关联
把多个来源中指向同一件事的条目组织起来。当前核心模型缺少通用事件层。

依据：调度器、持久化实现、MCP、AI 调用。

延伸 10 / A PRACTICAL REBUILD

先跑通一个有用的监控闭环。

下面是建议实施顺序，不是已完成的改造。优先验证信息是否有用，再扩大平台范围和产品机制。

01
领域解耦

把普通信息放进系统

移除链与支付依赖；建立主题、来源、条目和事件模型；替换身份和授权；规则与 AI 都支持普通文本。

验收：不含币名或地址的信息也能被保留。
02
最小闭环

少量来源，可靠交付

先接网页、RSS、GitHub，再按需要接 X 和 Telegram；做到增量读取、原文留存、来源健康状态和基本通知。

验收：重启后继续；抓取失败与没有更新可区分。
03
信息质量

区分重复报道与真实进展

加入去重、实体别名、事件关联、通知去重和每日摘要；保留冲突说法，允许用户纠正或合并事件。

验收：同一公告只提醒一次，新增日期或结论仍提醒。
04
真实评估

用用户任务衡量价值

人工抽样标记相关性，记录首次发现时间、无关提醒、重复和遗漏；根据实际规模决定数据库与独立后台任务。

验收：每条提醒都能追溯原文和触发理由。

开始实施前，需要确定的产品问题

关注什么？ 项目、竞品、人物，还是行业主题？

信息来自哪里？ 必须支持的平台和公开范围有哪些？

什么值得提醒？ 即时变化、重要进展，还是每日汇总？

怎样判断有用？ 用户反馈、人工抽样和发现时效如何记录？

适合借鉴的部分

来源适配、按偏好分析、增量提醒与反馈闭环已有清晰样本。若目标是长期维护的通用产品，优先抽出监控内核与来源适配器，重新组织主题、事件、身份和存储层，会比让币圈模型继续承载所有信息更清楚。这是结构判断，尚无工期或性能实测。
