Atlas：把模型能力，
组织成资产制作流程。

Atlas 是供代理使用的技能规范与辅助脚本，组织 2D/3D 资产生成、质量检查和引擎接入。底层能力来自模型与执行工具；它的工程意义，是让生成结果更容易成为可继续编辑、验证和交付的资产。月门水庭是我们独立验证 Blender 脚本路线的实验。

源库能力
覆盖场景图、精灵、动画、地形、界面图标、角色一致性，以及三维模型、PBR 材质、着色器和 Three.js 接入。
实现原理
先约定规格，再选择生成器、DCC 脚本或程序几何；模型调用工具执行，按检查与视觉反馈修正，最后导出并接入引擎。
价值与意义
模型负责理解、规划与生成，库组织工具、流程和验收。三维结构可复用机位、定向修改并承载交互；效率与质量增益仍需对照评测。
可扩展方向
可控参数编辑、多生成器适配、资产质量与设备性能、资料和任务交互；用途可探索展陈、教学、产品展示、镜头预演与游戏。
本次实证与边界
原创图 → 模型写 Blender 脚本 → 可编辑工程 → GLB → 网页真实 3D。未完整执行 Atlas 技能包，未调用专用图生 3D，也未证明准确重建、量产可用或商业收益。

01 / 核心结论

价值的核心，是模型构建和修改三维的能力。

本次实际验证的是：模型理解一张参考图，规划场景，编写普通建模代码，再让 Blender 执行，得到可编辑、可重新渲染、可放进网页的三维结构。

“模型生成 3D”在这里描述一条完整的工具使用路线。模型通过代码表达物体的形状、位置、材质和灯光，建模软件把这些指令落实为网格与场景。生成完成后，工程可以独立保存，网页也可以直接载入它，继续换机位查看。

把结论分成三个层次

能力层：模型能否把视觉意图转成可执行的三维构建方案？本次有实际结果。

流程层：工具、规范、检查与反馈是否能让结果更稳定、更容易交付？有工程意义，但本次没有做带 / 不带 Atlas 的对照实验。

产品层：是否更省钱、更省时、更有用，能否进入实际业务？需要进一步测试，不能由一个成功场景直接推出。

因此，“价值就是模型生成 3D 的能力”抓住了技术核心。更完整的说法是：模型能力提供可能性，工具与流程把能力落实成资产，具体任务决定这种资产有没有使用价值。

这份记录描述可观察的行为与结果。仅凭演示，无法断言模型内部采用了何种三维表征，也不能据此推断它对所有场景都同样可靠。

02 / 原帖与 Atlas

先分清：作者展示、公开工作流和本次实作。

研究起点是 Shikhar 的场景演示。我们取得了展示画面的参考线索，但没有取得原作者的场景工程、完整提示词、相机参数和逐步制作记录。原视频具体怎样做出来，仍有未确认部分。

作者公开的 Atlas，在本次固定版本中是一组供代理使用的技能说明与辅助工具，覆盖图像、资产与引擎接入。README 将它描述为可移植的资产制作技能；它没有把工作流限定为某一个生成模型。

model3d-gen 明确列出三类实现途径：调用三维生成工具、通过 Blender 等软件写脚本建模，以及程序几何。它还规定资产规格、清理、检查和视觉复核等步骤。asset-core 强调交付约定与验证；threejs-pipeline 讨论在引擎中加载、布光、压缩和检查。

对象能够确认不能由此确认
作者原视频展示了一个场景效果，是本次研究的起点。每个物体的生成方式、是否调用专用图生 3D、自动化程度与完整耗时。
Atlas 固定源码提供工具选择、资产规范、清理、验证和展示的工作流。原视频一定按这份固定版本制作，或只安装技能就能保证相同效果。
本次月门水庭独立生成参考图、编写 Blender 脚本、实际渲染，再导出网页模型。对 Atlas 原视频制作过程的完整复现，或对 Atlas 增益的独立评测。

Atlas 的规范目标包含可用于引擎的资产，但规范中写了质量要求，并不等于所有结果都已达到该要求。本次也没有安装并完整执行 Atlas 技能包；我们研究其方法，再独立验证脚本路线。基础模型能力、技能说明、软件执行和视觉质量，应当分别评估。

上游固定版本：b283a80dcb6db9068ba368fedfca783f5164ba06，记录许可证 MIT。这里引用的是其公开工作流，不把原帖的场景素材视为本次制作资产。

03 / 三维资产Blender执行几何、材质与渲染
04 / 网页体验浏览器渲染器载入模型，响应操作
环节输入 → 输出本次具体工作
图像生成文字描述 → 二维参考图生成紫藤、水池、石门与天球仪的原创暮色庭院；没有传入作者的图片。
模型理解参考图与目标 → 场景方案识别元素、估计比例、坐标和机位，把复杂物体拆成可构建的部分。
模型编程场景方案 → Python 脚本编写网格、环带、枝干、批量叶片、程序材质和灯光代码，并按反馈修改。
Blender 执行脚本 → 实际场景创建网格、材质、灯光和相机，保存可编辑工程。
Cycles 离线渲染场景与机位 → 像素图计算遮挡、照明、反射等成像结果，输出主视角、侧视和环绕帧。
导出与网页已保存工程 → GLB → 交互合并网格、近似转换材质、压缩；Three.js 载入后允许旋转、缩放和平移。

模型不需要在每一帧重新“想象”整个庭院。几何一旦生成，后续画面由同一套空间结构计算。浏览器里的拖动是相机操作，模型服务没有参与每次旋转与缩放。

本次由模型在对话中分析、编写、执行并观察结果；用户提供目标与方向。场景逐步形成于这些工具调用与定向修改中。我们没有把它封装为一次提交即可稳定完成的无人值守生成服务。

04 / 路线

“看图做 3D”可以指几种不同的过程。

用户最初问的“分析图，再借助生成 3D 的能力”可以作为宽泛概括。具体实现必须再分：看图后写建模代码，与把图片输入专用三维生成器，走的是不同链路。

路线如何得到三维需要注意本次状态
单图理解 → 脚本建模模型从图中归纳物体、尺寸与关系，输出建模程序，由软件执行。结构与参数方便定向修改；细腻形体、材质和不可见部分取决于建模方案。已实际执行
单图 → 专用三维生成器把图片交给专门输出三维表示或网格的模型 / 服务，再整理资产。结果仍需检查比例、表面、拓扑、材质和可编辑性；质量取决于具体工具。本次未调用
实拍多视图 → 重建利用同一真实物体的多个观测，约束相机、形状或外观。需要对应关系、覆盖度、稳定主体与合适的成像条件；多几张图也不保证成功。本次未测试
生成多视图 → 再建三维先让图像模型补出不同角度，再作为后续三维流程的输入或参考。生成图之间可能在物体、尺度和遮挡上矛盾，必须检查视角一致性。本次未测试

这里还有两个容易混在一起的问题。

“生成新的结构”和“恢复真实结构”：给一张概念图做出相近主题的场景，可以在不确定处主动设计。要恢复某个真实场所的准确形状，则需要额外观测、尺度与检验。本次属于参考图指导的近似构建。

“用了图像模型”和“用了图生 3D 模型”：本次确实先用了图像生成来做概念图，之后的建模由模型编写普通代码完成。这两步承担不同角色，参考图没有被当作贴图或相机背景塞进三维场景。

单图的背面没有唯一答案。一张正面图可能对应不同的墙厚、连接方式与背部结构。本次未做自动深度估计、相机标定或多视角匹配，相关尺寸与不可见部分由视觉估计和补建得到。

上表后两种路线是方法区别与条件分析，本次没有运行其重建算法，也没有进行不同路线的质量、速度或成本排名。

05 / 实验关系

先试复现，再换成自己生成的参考图。

第一轮：参考原帖展示画面的秋日庭院。

最初取原帖视频的展示画面作为视觉参考，独立用 Blender 脚本搭建白石建筑、红叶树、台阶与远景。那张参考已经是渲染完成的画面，我们没有取得作者原始概念图与工程。第一轮主要证明：凭视觉理解和脚本，可以搭出具有相近主题与纵深的场景。

这轮经历了面朝向、光照、拱廊方向、后景雾和薄石块尺寸等修正，过程保留在 历史研究记录。它不是原作者场景代码的运行结果。

第二轮：先生成原创“月门水庭”，再建立三维。

用户随后要求先自己生成图片。我们新建了紫藤、水池、月门与天球仪的主题，生成时没有输入前一轮图片。然后重新分析、编写场景脚本、实际渲染和调整，并在后续把同一工程接入网页。

两轮只复用了本项目自己写的基础网格辅助函数。月门水庭的布局、植被、天球仪、石门、灯笼和程序材质属于本次独立制作，没有复制上游示例工程或场景脚本。

换成原创参考图以后，实验链路更完整：我们同时掌握视觉目标、建模代码、实际工程、导出资产和网页表现，可以逐步检查每个环节，而不只对着作者的一张展示图讨论效果。

06 / 场景实现

把画面元素拆成能执行的构建规则。

模型先判断“画面里有什么”和“它们怎样摆放”，再选择合适的几何表达。主体并非一个不可分的整体：圆门、桥面、圆台、花簇与灯笼都能拆开构建，最后组合成同一场景。

元素本次具体实现当前简化
圆形月门56 块环形石块，保留接缝，加内外细边线与倒角。雕刻、石材磨损与装饰细节有限。
天球仪相互倾斜的金属带、黄道带、刻度小点、轴杆、底座与发光球体。结构服务画面主题，没有验证真实仪器的机械功能。
水池、桥与圆岛独立池底、池岸、带细小起伏的水面网格、铺石桥与分层圆柱台。水面静态，没有流体模拟和行走碰撞。
紫藤树管状主干、根系、分枝，批量叶片和成串花朵网格。枝形仍有规则感；自然生长、树皮和叶簇层次较简化。
三孔拱廊有厚度的石柱、拱券、拱上填墙与连续檐口。复杂雕花与建筑构造细节未完全展开。
灯笼台座、青铜框、装饰卷纹、灯芯、屋顶与局部点光源。灯具细节与材质质感没有达到参考图丰富程度。
远山、湖、新月程序山脊、远景湖面、新月轮廓网格与离线后景雾。远山是舞台式景层，背面与任意远距离浏览的完整性有限。

完成一遍构建，还要看实际渲染。

第一版视线偏高，前景灯笼被裁切，远山偏高偏暗，拱廊顶部还出现不应有的小洞。之后降低机位、调整圆门与拱廊、补齐石层、移动新月并改善树皮与灯光。最终图来自多轮定向修正。

这体现了模型的两类能力：把语义和形体拆成程序，以及根据实际输出定位问题并修改程序。本次没有建立自动相似度评分器，也没有证明仅靠一句提示词就能稳定达到目标效果。

展开技术细节：代码如何表达形体？

完整代码见 场景脚本 与 基础网格函数。例如月门使用中心坐标、内外半径、厚度和石块数量；枝干使用路径点与各点半径；花朵按固定随机种子在枝条周围批量布置。修改这些规则后，需要重新执行脚本并检查结果。

程序几何包含实际顶点、面、法线和材质引用。建模代码的可修改性与最终几何精细度是两回事：能调整参数，并不意味着自然树形、雕刻和纹理就足够好。

08 / 从工程到网页

同一份几何，换一种渲染与操作环境。

  1. 读取已保存的 Blender 工程。导出脚本对源文件计算哈希，在内存中处理场景，结束时再次确认原文件未改写。
  2. 取出实际求值后的几何。倒角等修改器的结果进入导出，按集合与材质合并物体，减少浏览器需要提交的绘制批次。
  3. 转换适合网页的资产表达。程序材质转为近似 PBR 色值；几何以 Draco 压缩写入自包含 GLB。
  4. 在浏览器中重建展示环境。加载模型，建立相机、天空、环境光、阴影、距离雾和水面反射，再接入操作控制。
内容网页如何处理实际影响
场景几何、倒角从源工程求值后导出；未做几何减面，采用量化压缩。保留主体形状与空间关系，压缩会引入有限坐标 / 法线精度变化。
大量独立物体合并为集合与材质批次。更便于渲染，但网页 GLB 的逐物体编辑粒度下降；细改应回到原工程或脚本。
程序材质转换为近似颜色、粗糙度、金属度与发光参数。没有完整转移 Cycles 节点网络，石材、树皮等细节表现发生变化。
灯光、相机与色调在 Three.js 中另外设置。实时画面与离线图的明暗、色温、质感不完全相同。
水面普通查看时用实时平面反射与静态扰动；线框时可检查原水面几何。倒影随相机变化，但没有流体模拟，反射增加额外渲染工作。
远景体积雾省略原雾容器，使用距离雾近似。空气感与离线体积效果有所不同。

网页提供旋转、滚轮与按钮缩放、平移、庭院全景 / 原图机位 / 月门 / 天球仪四个预设视角，以及自动环绕、线框和全屏。鼠标操作已在浏览器实际验证；手机宽度布局已检查，未用真实手机硬件完成触摸与性能验收。

这里的“压缩成 3.62 MB”指下载文件大小。它不等于运行时内存，也不保证帧率。实际负载还取决于可见几何、反射、阴影、像素数量和设备。本次已经做了合并与压缩，仍没有完成低端设备和多浏览器性能基准。

09 / 价值判断

技术能力的价值，要在任务里兑现。

第一层：降低表达三维方案的门槛。

本次展示了把文字和参考图转成建模步骤的可行性。用户可以描述想要的物体与变化，模型编写工具能执行的代码，再根据结果继续修正。它把一部分“怎样操作软件”的工作转成了“怎样描述与检验目标”。

第二层：生成的是可以继续工作的结构。

保存后的场景允许换机位、换灯光、改尺寸、改布局和再渲染。相较只交一张成图，这种产物能承接更多后续变化。当前网页只暴露相机查看；改石门、移动树等操作仍通过原工程或脚本完成，需要重新检查和导出。

第三层：工作流有自己的工程价值。

选择工具、安排步骤、保存版本、处理导出、管理依赖、验证结果和记录局限，都会影响模型能力能否稳定交付。Atlas 这类工作流的价值可以放在这一层理解。是否显著提升成功率、质量或效率，需要用对照测试衡量，本次没有得出增益数字。

什么时候三维更有意义？

当你需要同一空间的多个机位、明确的结构变化，或物体与操作之间的关系时，三维结构更值得继续投入。

如果需求只是交付一张静态氛围图，直接使用生成图往往流程更短；这次的建模步骤未必带来足够收益。

仍没有证明的商业结论。

我们没有完整记录模型调用成本、人工整理时间与失败率，也没有同传统建模或其他三维生成器做公平对照。因此，“已做出”可以成立，“更便宜、更快、可量产”仍需验证。最终价值取决于质量要求、修改频率、使用次数、目标设备和后续整理成本。

10 / 应用方向

游戏是一种用途，三维也能承载别的任务。

“能构建的场景”可以理解为具有物体、空间关系、相机和状态的环境。下面是可探索的方向，不表示这些产品功能已经在月门水庭中完成。

方向三维可能带来的价值真正落地还要补什么
镜头预演与内容制作复用一个场景比较构图、镜头路径与光照。场景质量、镜头语言、输出稳定性与后期流程。
空间与展陈原型比较物体摆放、动线和观赏角度。真实尺寸、布局约束、可达性和实际场所核对。
产品与方案展示允许用户转动物体、观察部件与不同配置。准确产品数据、材质、交互与配置规则。
虚拟展览让空间组织内容，物体成为信息入口。导览、标签、检索、内容维护与无障碍访问。
教学与结构讲解从多个角度解释组成、位置与遮挡关系。知识准确性、标注、步骤与教学效果验证。
工作空间与任务界面把对象和位置映射为任务、资料或状态。真实业务接入、操作反馈、可用性与效率证明。
游戏关卡与互动原型快速试空间氛围、路线和视觉主题。碰撞、导航、角色、动画、逻辑、资产预算和引擎验收。

能旋转查看，是进入应用的起点。要让用户点击天球仪打开资料、在庭院行走、操作门或完成任务，还需要事件、状态、约束、反馈与数据。把一个静态场景放上网页，尚不能代表这些功能已经实现。

也不必为了三维而三维。如果一张图、一张表或普通二维页面已经更清楚、更快地完成任务，应当据此选形式。应用价值应当由任务完成情况和用户行为来证明。

11 / 边界

一次可运行的实验，仍有明确的能力边界。

容易扩大理解的说法本次证据支持到哪里缺少的验证
“从图准确恢复了 3D”按视觉估计构建了相近主题的三维场景。相机标定、尺度依据、完整观测与独立误差评估。
“原作者就是这样做的”公开工作流允许此路线，本次独立路线可执行。原视频工程与完整制作记录。
“安装技能就能达到示例质量”技能说明可以组织工具、步骤和检查。不同模型、输入、预算和执行环境下的成功率。
“所有形体都能同样做出来”建筑和环带等规则结构能够落地，自然形态仍较粗糙。角色、复杂雕塑、柔性结构等独立样本测试。
“模型能看，就能一次写对”本次需要多轮渲染反馈与代码修正。错误率、修复次数、任务难度与稳定性统计。
“网页显示成功，已能直接商用”浏览器内可交互查看。用途对应的质量、设备、可用性、内容和交付验收。
“静态水面意味着流体模拟完成”有水面几何、材质与实时反射。流动、碰撞、波动传播与物理参数。

此外，这个项目没有建立工程精度、制造约束或实际结构安全验证。脚本中的尺度服务于画面布局，不能直接作为真实建筑、机械或生产图纸的依据。角色绑定、骨骼、复杂动画、游戏碰撞与导航也不在本次已完成范围内。

当前视觉差距主要来自造型、结构细节、材质与光照的选择。单纯提高渲染采样数，不能把规则分枝变成自然树形，也不能补出尚未建模的雕刻与云层。

图像生成记录到了工具入口与输入输出，尚未形成用于跨模型评测的完整模型快照、全部提示历史和统一计费日志。本次可追溯的脚本、工程和输出，不能替代完整的模型能力基准。

12 / 后续验证

下一步应增加证据，而不只增加展示效果。

以下是待执行的实验方向，页面没有把它们记为已完成。

  1. 测试可控修改。提出“月门加大、桥改弧线、树向左移动”等明确要求，检查目标是否实现、其他结构是否受损，并保留修改前后机位一致的图像。
  2. 换一组独立参考图。覆盖不同建筑、自然物体、尺度与风格，记录失败案例与迭代次数，避免只凭一个庭院判断通用性。
  3. 对照不同生成路线。在同一输入、预算与验收规则下比较脚本建模、专用图生 3D 及传统制作；记录完整耗时、调用成本、整理时间和最终可用性。
  4. 测量网页表现。在目标设备、浏览器、分辨率和典型机位上记录加载时间、帧时间、内存与反射成本，再决定减面、实例化、细节层级或贴图方案。
  5. 加入一个有目的的交互。例如点击天球仪查看结构说明，或用庭院展示一组资料；用真实任务判断三维是否改善理解与操作。
  6. 提高流程可重复性。把布局、尺寸和材质要求整理成明确参数，保存执行环境与版本，增加语义检查，观察能否降低修改与返工成本。

更有说服力的下一步，是验证一次需求变更、记录一次完整成本，或让一个真实任务在三维中完成。它们分别回答“可控吗”“划算吗”和“有用吗”。

13 / 常见问题

把讨论中的疑问逐个说清。

18 个问题，可逐项阅读或全部展开。

1. 本质是不是模型生成 3D 的能力？

是技术核心的一部分。更准确地说，本次验证了模型通过视觉理解与编程使用三维软件的能力。保存、验证、导出与交互流程把它落实成可继续使用的资产；是否创造产品收益仍需另外证明。

2. 场景到底是模型做的，还是 Blender 做的？

两者承担不同职责。模型规划并写建模代码，Blender 执行代码、建立三维结构并计算图像。描述创作与控制过程时，可以说模型通过 Blender 制作；描述几何与渲染执行时，Blender 是执行工具。

3. 这次是否调用了专门的图生 3D 服务？

没有。本次先通过图像生成获得概念图，之后独立编写 Blender Python 来建模。没有把这张图提交给直接输出三维网格的专用模型。

4. Atlas 自己是不是训练出的三维生成模型？

本次核对的公开内容是一套技能说明与辅助工具，其三维技能允许选择不同生成工具或代码路线。现有源码证据没有显示它本身提供三维生成权重，也不能用这一点反推原视频的全部制作过程。

5. 如果基础能力来自模型，Atlas 还有什么价值？

把工具选择、资产规格、清理、验证和引擎接入写成可重复的工作流程，有工程价值。至于它能提升多少成功率或节省多少时间，本次没有对照实验，无法给出增益数字。

6. 当前用的是作者的示例工程吗？

月门水庭由本次原创参考图出发独立构建。此前秋日庭院曾以原帖展示画面为参考，但也没有取得或执行作者的工程与脚本。两轮的来源和差别都保留在记录中。

7. 多角度图片会不会直接解决问题？

多个一致的真实观测可以增加约束；由模型生成的多角度图还需要检查彼此一致性。两种情况不能混为一谈，几何、相机、遮挡与材质仍需处理。本次没有实施多视图重建。

8. 为什么从正面像，侧面可能仍有问题？

参考图没有给出全部结构，本次的厚度、背面、连接和尺度有估计成分。真实几何保证这些部分可以从新机位计算，但不保证它们符合参考场景的真实结构或同等美术质量。

9. 网页里的旋转需要继续调用模型吗？

不需要。模型已经导出为文件，浏览器载入后由相机和渲染器响应操作。当前查看器没有在每次拖动时调用语言模型、图像模型或三维生成服务。

10. 网页画面为什么与 Blender 渲染不同？

几何来自同一工程，但程序材质、体积雾、灯光和成像设置没有原样搬到浏览器。网页以近似 PBR 材质、实时光照和反射进行展示，因此明暗、色温和细节存在差异。

11. 网页上能直接移动树、改桥或改门吗？

当前界面提供相机查看与线框等操作，没有开放场景编辑。可以修改原 .blend 工程或建模脚本，再渲染和导出。网页模型已合并批次，逐物体编辑还需要额外组织与交互开发。

12. 这些水波、花朵和灯笼在动态模拟吗？

没有物理模拟。水面反射会随相机变化，波纹是静态几何或着色扰动。花朵与灯笼保持静态，环绕视频只移动相机。

13. 能否直接放进游戏？

GLB 可以作为继续集成的资产起点。当前没有完成特定游戏引擎的性能预算、碰撞、导航、角色动画和关卡逻辑验收，不能把网页载入成功直接等同于游戏量产完成。

14. 最终用途是否主要还是游戏？

游戏适合使用三维场景，但镜头预演、空间方案、产品展示、教学、虚拟展览与任务界面也可探索。选择哪一种，应取决于三维是否帮助用户理解、选择或操作。

15. 已经证明比传统建模更快、更便宜了吗？

没有。现有记录只覆盖部分单次脚本运行与渲染，没有完整的人力、模型调用、失败与整理成本，更没有同条件的人工制作对照。

16. 为什么不继续提高采样，让它更像参考图？

采样主要改善渲染噪声。缺少自然枝形、雕刻、材质层次与合适构图时，需要修改场景和美术方案，单靠采样不能补足这些内容。

17. 保存后离开模型，结果还能继续使用吗？

可以。Blender 工程可以重新打开并渲染，网页 GLB 可以继续载入查看。本次做过保存后重开与多视角渲染检查。后续编辑仍需要相应软件或新增界面。

18. 怎样才算这个研究真正更进一步？

让一条新的明确修改要求稳定落地，记录完整过程成本，并在一个具体用途上验证收益。继续产出更漂亮的截图有展示意义，但不能代替可控性、稳定性与实际使用价值的证据。
