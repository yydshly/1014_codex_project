RESEARCH SUMMARY / EIGHT QUESTIONS

能力、原理、启发，以及扩展的意义。

八项摘要串起源库能做什么、怎样运行、我们学到什么与如何继续用。沿用既有总图引导阅读，来源和规则可向下逐项追查。

01 / 源库能力

持续发现币圈信息中的变化

CrawlHive 将用户指定的账号、频道、网页、词表与行情条件组织成监控任务，通过 Grok 搜索 X、读取 Telegram 公开预览、比较指定网页新增文本、调用 DexScreener 接口 获取候选，再经规则或可选 AI 提取、代币关联、去重与风险检查，保存和交付私有信号，追踪后续价格表现。

它是领域化监控应用；本研究阅读固定源码，尚未运行上游服务。

02 / 工作原理

配置关注对象，持续把变化变成信号

来源控制 → 信息搜索 → 信息过滤 → 信息呈现是主线。一个原库任务选择一种来源，调度器周期触发适配器：X 提交搜索意图，频道用消息编号追增量，网页建立基线再比较新增文本，行情接口按列表、关键词或地址读取；候选再进入规则／可选 AI、关联检查、去重、保存和私有交付。

搜索词、程序硬规则与模型偏好分别生效；不同来源的“关键词”不保证同一种约束。展开原理与逐来源例外 →

03 / 带来的思考

沉淀来源接入，也沉淀处理经验

公开平台名单容易获得，值得积累的是选哪些具体来源、怎样接入、覆盖到哪里、如何持续运行，以及信息为何留下。接入适配、调度增量、过滤去重、证据保存与交付共同构成可复用经验。钱包、积分与行情评价服务原作场景，我们探索 AI 信息时需要重新设计它们。

现有研究尚未证明独占数据、难复制算法或长期效果；价值应由真实任务验证。

04 / 我们探索了什么

从四环节拆解，到独立 AI 工作台

先逐来源追查来源控制、信息搜索、信息过滤、信息呈现的实际实现，整理总图、26 条源码依据和 21 项来源接入档案；再从零构建“知向”，探索方向 × 目的 × 来源 × 规则的使用方式。2026-10-15 实采 4 个公开来源、51 条条目，验证筛选、匹配原因、收藏、导出与本地主动刷新。

独立原型没有调用上游业务或模型；来源覆盖和长期收益仍待评估。

05 / 哪些来源可以获取信息

原库 4 类、原型 4 个、候选 13 项

原库覆盖 X、Telegram、公开网页与 DexScreener；原型已接入 Hugging Face Blog、Google AI Blog、GitHub AI & ML Blog 与 GitHub 仓库搜索。候选再补官方公告、HF 模型与 Spaces、arXiv、GitHub Releases、Hacker News、Product Hunt、中文媒体、YouTube、Reddit 和 X 官方 API。

RSS / Atom、API、公开 HTML 各有覆盖、认证、费用与稳定性边界；候选未等于已接入。查具体入口和请求示例 →

06 / 我们怎样处理信息

受控获取 → 规范整理 → 规则筛选 → 留存研究

原型读取固定 RSS，并按预设 GitHub topic 搜索，保留原链接、来源、日期和短摘；同 URL 合并。选择方向与内容类型后，对标题、短摘和主题标签执行搜索词、包含词任一／全部、排除优先、来源开关和时间范围检查，再按命中数或时间排序，展示匹配理由、原文、收藏与导出。

关键词筛选当前已采集数据；没有全网语义搜索、模型摘要、事实核查或语义事件聚类。

07 / 可扩展思路与意义

把领域监控，变成可配置的研究入口

围绕方向 × 目的 × 来源 × 规则重建主题、条目、事件与证据模型，替换币名、钱包和币价评价；先把 RSS／API 来源接稳，再补游标、重试、健康状态和定时交付，后续按任务需要增加模型辅助分类、事件聚合、跨来源核对与用户反馈。

意义在于复用关注方案、减少重复获取与阅读、保留可追溯证据，连接“发现 → 判断 → 行动”。后续能力仍待实现，省时、漏报和费用需对照评估。查看扩展设计与实施顺序 →

08 / 使用场景与我的价值

跟动态、找产品、研究开源与已知目标

AI 信息跟进：组合公告、论文和讨论，找值得核实的更新；产品发现：收集上新、演示与反馈，形成待试用清单；开源研究：结合仓库、许可证和版本信息决定读什么、试什么。进一步可扩展为指定项目、竞品文档和行业主题监控。

预期减少逐站查找、复用关注规则、保留来源证据和下一步；节省时间、漏报、重复与费用需要实际记录。

01 / 原库能力是什么

面向币圈的私有信息监控应用

用户把关注对象、来源、关键词和规则写成任务。系统从 X、Telegram 公开频道、指定网页、DexScreener 获取候选，处理后保存并交付信号，还带有代币扫描、风险检查和行情追踪。

  • 通用可借鉴：来源适配、任务配置、增量游标、调度、筛选、去重、持久化与交付。
  • 领域专用：币名与地址、链、流动性、代币风险、钱包身份、积分和行情结果评价。
  • 使用边界：一个任务对应一种来源；源码有实现，尚未证明长期运行质量。它不是全网全量爬虫，也没有通用的跨平台事件融合。

原库是可研究的完整应用样本；用于普通信息监控时，需要重新设计领域模型。查看 12 项能力与源码依据 →

02 / 原理是什么

把外部变化，转成用户关心的信号

  1. ① 定义范围来源、目标、词表、规则
  2. ② 持续获取调度、来源请求、增量比较
  3. ③ 判断去留规则 / 可选 AI、关联与检查
  4. ④ 保存交付私有信号、来源引用、后续回看

这些环节里，搜索与订阅的作用不同：X 可提交搜索意图，Telegram 读取给定频道，网页比较给定 URL 的新增文本，DexScreener 则有列表、搜索和指定地址等路径。

关键词也不统一：部分路径是本地硬规则，部分只是模型偏好。最终处理包含代币解析、去重与风险检查，存在分支和例外。

同样写“包含关键词”，不同来源未必执行同一种过滤。查看逐来源规则与例外 →

03 / 引发我们的思考

应该沉淀什么，才能换一个场景继续用？

  • 来源名单：帮助发现入口，但公开平台名称容易复制；还要知道具体作者、频道、仓库和订阅地址。
  • 接入知识与代码：哪些接口可用，能拿到什么、如何搜索、是否要授权、怎样增量，以及失败怎么恢复，能节省重复摸索。
  • 持续处理流程：从一次读取走到稳定监控，还需要重试、游标、去重、原文证据、健康状态和交付管理。
  • 判断独特价值：现有证据没有证明原库拥有独占数据、难复制算法或长期优于其他方法的效果；不能把代码存在直接换算成商业壁垒。

对我们的场景，最值得借鉴的是“接入实现＋可持续处理经验”。币、钱包、积分和行情评价可按需求剥离，监控内核仍有参考意义。

04 / 可扩展思路是什么

以“方向 × 目的 × 来源 × 规则”组织产品

方向回答研究什么，例如智能体、编程、多模态；目的回答要找到新闻、可试用产品，还是值得读源码的项目；来源与规则共同决定范围。

  • 先通用化：将代币信号拆成主题、来源、原始条目、事件、证据与交付；使用普通用户身份及合适的价值反馈。
  • 再积累来源：维护可搜索的接入目录，每个来源记录价值、入口、认证、字段、查询、增量、限制与验证日期。
  • 再提升处理：按需要补原始证据留存、实体别名、事件关联、冲突说法、模型分析和重要变化提醒；这些需要独立实现和验证。
  • 围绕真实任务评估：相关性、覆盖、重复、发现时效、时间与费用都应通过实际使用记录。

现在已经做出的“知向”验证了范围筛选与阅读收藏的体验；完整通用监控产品还有后续工作。体验独立原型 →

RSS / ATOM

订阅发布出来的条目

读取订阅地址，解析标题、链接、日期和来源提供的短摘，用稳定 ID 或 URL 判断新条目。通常先拿到最新列表，再按本地规则筛选；能否服务端搜索取决于具体来源，订阅也不保证有全文。

OFFICIAL API

按接口能力查询结构化数据

调用官方或服务商接口，按支持的词、账号、分类等筛选，处理分页、时间游标、限流与错误。需要的密钥或授权放在服务端；搜索权限、历史范围和费用逐平台确认。

PUBLIC HTML

读取特定公开页面的变化

获取页面并提取正文，保留基线后比较新增或变化内容。原库不执行页面 JavaScript；登录后内容、动态页面、结构变更和反爬机制，都可能影响获取范围与稳定性。

可控的来源粒度：平台 → 作者 / 频道 / 仓库 / 页面 → 内容类型。

例如 GitHub → 指定仓库 → Releases；arXiv → 研究分类＋查询词；Telegram → 公开频道。先用搜索发现目标，再用订阅或增量监控跟踪目标，是两种需要分别设计的获取方式。

01 / SOURCE CONTROL

来源控制：先决定去哪里看。

来源决定信息能否进入系统。用户选择来源类型和目标，系统在这个范围内周期运行；目前一个任务对应一种来源。

对应价值

把关注范围交给用户控制，减少无关来源，让每条信息的来历更清楚。

固定版本已有的 4 类监控来源；手机上可横向滑动表格
来源用户指定什么实际获取方式覆盖边界
X社交帖子@账号、查询词、关键词Grok 的 x_search 搜索需要 API 密钥；结果不等于完整订阅信息流
Telegram公开频道公开频道名称或链接频道网页预览 t.me/s只读公开预览；不读私有群或全部历史
公开网页官网／博客／文档具体 URL取 HTML，比较新增文本行不执行 JS、不递归全站；保存前 12,000 字符用于比较
DexScreener代币与交易对链、数据流、关键词或观察地址档案、推广、搜索与行情接口依赖第三方覆盖，不是完整链上索引器

02 / SEARCH & COLLECTION

信息搜索：主动找，或持续盯住。

搜索尝试找到相关内容；轮询则反复观察指定目标，等它出现更新。这个库同时使用两种获取方式。

对应价值

让系统按周期获取新内容，减少用户重复检索和反复打开页面的操作。

SEARCH / 主动检索

给出查询条件，向来源找

X 将账号、查询文字和时间条件交给 Grok；DexScreener 的 search 数据流按关键词查交易对。

WATCH / 指定目标轮询

给定目标，读取新变化

Telegram 按消息编号读取；网页先保存基线再比较新增文本；档案与推广列表也会定期拉取。

04 / PROCESSING & PRESENTATION

信息呈现：从候选，变成带来源的提醒。

呈现之前，还有结构化、条件检查、身份关联、去重与可选分析。用户看到的是处理后的信号，并非全部采集内容。

对应价值

让用户知道发生了什么，能回到原文核实，并在之后判断提醒是否有用。

  1. 01

    提取候选字段

    摘要、信号类型、置信度、来源 URL，以及可选币名／地址。模型输出 JSON，规则路径则按固定逻辑构造候选。

  2. 02

    检查条件，关联代币并去重

    检查类别、置信度和排除词，尝试关联交易对并记录价格。按任务自己的“代币＋信号类型”在 12 小时内抑制重复；无代币时有其他候选键回退。

  3. 03

    可选 AI 分流与风险检查

    Jev 可按关注价值分流；支持范围内的代币进入安全检查。DANGER 过滤，预算不足延后；扫描连续第二次失败会放行无判定信号。

  4. 04

    保存信号，按归属交付

    保存摘要、引用、时间、归属和判定等。当前持久化以信号与状态快照为主，不能理解为所有原始消息都被完整归档。

  5. 05

    追踪后续，形成反馈

    关联代币的信号按窗口和涨幅目标追踪；无代币可处于未计分状态。普通信息的“有用／无关”和进展评价，需要通用化时另设标准。

技术词汇展开：RPC、MCP、游标、去重、置信度分别是什么？
RPC
向区块链节点询问状态的接口。通用版可随链上模块一起移除。
MCP
让助手调用应用工具的协议。协议连接成功与具体客户端兼容仍需分别验证。
游标
记住读到哪里，例如消息编号、上次运行时间或页面摘要，减少重复采集。
去重
判断两条记录是否重复。相同主题可能有不同进展，不能仅按主题全部抑制。
置信度
规则或模型给出的判断分值。未经校准时不能直接视为事实正确概率。
事件关联
把多个来源中指向同一件事的条目组织起来。当前核心模型缺少通用事件层。

依据：调度器、持久化实现、MCP、AI 调用。

真实评估

用用户任务衡量价值

人工抽样标记相关性，记录首次发现时间、无关提醒、重复和遗漏；根据实际规模决定数据库与独立后台任务。

验收：每条提醒都能追溯原文和触发理由。

开始实施前，需要确定的产品问题

关注什么？ 项目、竞品、人物，还是行业主题？

信息来自哪里？ 必须支持的平台和公开范围有哪些？

什么值得提醒？ 即时变化、重要进展，还是每日汇总？

怎样判断有用？ 用户反馈、人工抽样和发现时效如何记录？

适合借鉴的部分

来源适配、按偏好分析、增量提醒与反馈闭环已有清晰样本。若目标是长期维护的通用产品，优先抽出监控内核与来源适配器，重新组织主题、事件、身份和存储层，会比让币圈模型继续承载所有信息更清楚。这是结构判断，尚无工期或性能实测。
