### 核心环节一：来源控制

现有监控来源只有 X、Telegram、On-chain（DexScreener）和 Docs（公开网页）四类。每个任务选一种来源，再填账号、查询词、频道、地址或 URL，并设置周期和规则；一个主题跨多个来源，需要用户建立多个任务，当前没有共享主题与事件层。

要区分三种“来源”：四类采集器负责持续观察；RPC、GeckoTerminal 等给代币扫描补充权限、持币或行情数据，并不是新增的通用监控平台；RSS、GitHub Releases／Issues 是通用化建议，尚不是原作已有适配器。网页中的通用化演示也不改变这一点。[核心模型](https://github.com/h100envy/crawl-hive/blob/77cfe1c7a42f0d071bee49ac9ebb77fdf0556827/src/lib/types.ts#L3-L43)、[扫描依赖](https://github.com/h100envy/crawl-hive/blob/77cfe1c7a42f0d071bee49ac9ebb77fdf0556827/src/lib/server/scan.ts#L1-L17)

### 核心环节二：信息搜索

搜索与采集不是同一步，也不是每个来源都有搜索功能：

- **X**：`@账号`转成搜索账号限制，其他目标和关键词用 ` | ` 拼进 Grok 的“Search for”提示；另传账号、日期等工具参数。代码没有实现严格的布尔表达式解析，不能把这个拼接等同于可验证的 OR／AND 查询执行。[X 搜索代码](https://github.com/h100envy/crawl-hive/blob/77cfe1c7a42f0d071bee49ac9ebb77fdf0556827/src/lib/server/crawl/sources/x.ts#L11-L35)
- **Telegram**：先读取指定频道的公开预览，按消息编号找新内容，再提取和过滤。关键词不会搜索更多频道，也不能获得私有群或完整历史。[频道采集](https://github.com/h100envy/crawl-hive/blob/77cfe1c7a42f0d071bee49ac9ebb77fdf0556827/src/lib/server/crawl/sources/telegram.ts#L46-L66)
- **Docs**：直接读取指定 URL，比较新增文本行；不搜索全网，也不递归寻找其他页面。
- **DexScreener**：profiles／boosts 是先取列表；启用 search 才对前五个关键词分别调用搜索，随后将结果与列表、观察地址合并。[行情搜索与合并](https://github.com/h100envy/crawl-hive/blob/77cfe1c7a42f0d071bee49ac9ebb77fdf0556827/src/lib/server/crawl/sources/onchain.ts#L18-L30)

### 核心环节三：信息过滤

共享关键词函数只做忽略大小写的子串匹配：包含词任一命中即可，空包含词表不限制，排除词任一命中优先拒绝。它没有整词、分词或语义理解，`AI` 可以匹配 `chain`。词表按英文逗号拆分，去空白与空项，按原大小写去重，取前二十项，再把每项截为前六十字符。[匹配函数](https://github.com/h100envy/crawl-hive/blob/77cfe1c7a42f0d071bee49ac9ebb77fdf0556827/src/lib/server/crawl/analyze.ts#L52-L77)、[词表整理](https://github.com/h100envy/crawl-hive/blob/77cfe1c7a42f0d071bee49ac9ebb77fdf0556827/src/lib/spec.ts#L41-L45)

各来源并不始终执行同样的硬过滤。Telegram 无 AI 时检查消息原文，还要求币代码或地址；有 AI 时则把关键词、排除词和 instructions 交给模型作为偏好，没有先执行相同的逐条硬检查。模型输出“相关”不代表原文必然含包含词，也不保证没有排除内容。

Docs 在 AI 摘要之前，对**整批新增行**执行硬过滤：任一排除词可能使整次页面更新跳过；任一包含词也可能让整批变化进入后续处理。它不要求出现币名。[网页变化过滤](https://github.com/h100envy/crawl-hive/blob/77cfe1c7a42f0d071bee49ac9ebb77fdf0556827/src/lib/server/crawl/sources/docs.ts#L54-L84)

DexScreener 有一个容易误读的例外：只要 feeds 含 search，合并后的普通候选都跳过包含词硬检查，包括同时来自 profiles／boosts 的结果；仍检查排除词和行情条件。观察地址的量能分支还会提前绕过这里的关键词及行情阈值。后续 Grok 筛选仅在配置密钥且 instructions 非空时运行。[混合来源过滤](https://github.com/h100envy/crawl-hive/blob/77cfe1c7a42f0d071bee49ac9ebb77fdf0556827/src/lib/server/crawl/sources/onchain.ts#L46-L89)

最终 finalize 检查信号类别、置信度，并只对“摘要＋币代码”硬查排除词，**不复核包含词，也不重新检查完整原文**；随后再做代币解析、去重、可选 Jev 和安全检查。因此搜索词、原文硬过滤、AI 偏好和最终门槛必须分别解释。[最终处理](https://github.com/h100envy/crawl-hive/blob/77cfe1c7a42f0d071bee49ac9ebb77fdf0556827/src/lib/server/crawl/analyze.ts#L300-L351)

新增 keyword-lab 交互只复现词表整理与共享关键词函数，展示命中词和通过／过滤原因。它不执行上游采集、AI、币名条件或完整信号链路；通过实验不代表会产生最终信号。

### 核心环节四：信息呈现

最终信号保存摘要、来源链接、时间、币代码、置信度及可用的风险、价格上下文，归属于对应用户；页面私有收件箱与 Telegram 负责交付，MCP 提供授权读取，可选 Bot 补充关注建议。公开地图有任务活动不等于公开私有信号全文。[信号模型](https://github.com/h100envy/crawl-hive/blob/77cfe1c7a42f0d071bee49ac9ebb77fdf0556827/src/lib/types.ts#L104-L123)、[保存信号](https://github.com/h100envy/crawl-hive/blob/77cfe1c7a42f0d071bee49ac9ebb77fdf0556827/src/lib/server/store.ts#L971-L1033)

后续价格回看用于命中与声誉，不能当作事实核实或可成交收益证明。当前也没有通用事件合并和完整原文归档：信号主要保存摘要与链接，Docs 游标另存截断页面文本，不能据此称所有原文都有长期快照。通用版需要补原始条目、事件、证据、判断版本和投递记录，再决定何时提醒新进展。[命中规则](https://github.com/h100envy/crawl-hive/blob/77cfe1c7a42f0d071bee49ac9ebb77fdf0556827/src/lib/server/store.ts#L1152-L1178)

## 1. 项目到底是什么

CrawlHive 是一个面向 Meme 币的信息监控与风险扫描应用。用户指定来源、目标与偏好，由后台定时采集、规则或 AI 提取候选，关联代币，进行风险检查，再交付私有信号并追踪后续价格。

迷因币是由网络梗、社区或热点带动的加密代币，关注度对其讨论与交易有明显意义。这解释了项目为什么同时监控社交来源和行情。它的特定领域不应被误认为通用监控所必需的条件。

从结构看，可分为三个层次：

1. 信息监控内核：来源适配、周期调度、增量游标、规则、模型、通知。
2. 领域解释层：链、代币身份、持币、合约权限、价格和命中窗口。
3. 商业与社区层：钱包支付、付费期限、积分、声誉、市场、治理与回购。

上述分层是本研究的结构归纳。当前代码并没有把三层完全隔离；核心类型和状态模块混合了多类职责。

### “爬虫”“蜂群”“Agent”的准确理解

- 一个 Crawler 是带单一来源、多个目标、规则和周期的任务。它不是一台独立计算机，也不是一个天然拥有工具规划能力的自主智能体。
- 来源枚举只有 x、telegram、onchain、docs。单个任务的多个目标仍属于同一种来源。
- “Swarm”主要是多个任务共用服务并在地图中展示。没有看到节点间协商、P2P 网络或分布式调度实现。
- 用户可以创建多个不同来源的任务，但尚无通用的“一个主题 → 多来源 → 共享事件”模型。
- Grok、Jev、值班 Bot 与 MCP 助手有不同角色，不能将整个流水线统称为自主多 Agent 协作。

## 2. 来源能力与真实覆盖范围

| 来源 | 实际方法 | 输入和增量 | 重要边界 |
| --- | --- | --- | --- |
| X | Grok x_search | 账号、查询词、时间条件 | 需要 XAI_API_KEY；搜索覆盖和时效不等于完整订阅信息流 |
| Telegram | 请求 t.me/s 公开预览并解析 HTML | 消息编号游标，首次最后 5 条 | 不支持私有群、全部历史或任意媒体内容 |
| 网页 | 取 HTML、移除脚本与样式、比较新增文本行 | 首次基线、哈希与文本快照 | 前 12,000 字符；不执行 JS，不递归抓全站 |
| On-chain | DexScreener 档案、推广、搜索和交易对信息 | 链、地址、流动性、量、估值、年龄 | 来源是第三方聚合数据，并不是完整链上索引器 |

特别修正：共享的 extractByRules 要求币名或合约地址，普通文本会被跳过；但 docs 适配器有独立的 doc_update 生成逻辑，因此不含币名的网页变化仍可能进入后续流程。不能将“无币名就丢弃”扩大为全部来源的共同规则。

whale_buy 的条件是观察地址的五分钟成交量超过小时均值的三倍且超过 1,000 美元。成交量包含的活动不等于已确认的巨鲸买入，源码标签应还原成数据含义。

## 3. 一条信息的实际处理链路

### 3.1 调度

应用启动进程内定时器，每 15 秒检查到期任务。最多 3 个任务并行，单次等待限制为 4 分钟；X 还受各档位最小间隔与可配置下限控制。失败有退避逻辑，多个链上请求共用 RPC 限流设施。

这说明“持续监控”需要后台进程持续在线。它并非毫秒实时，也不能因为有多个任务就推出分布式高可用。

### 3.2 提取

有 Grok 时，将近期条目与用户偏好传入模型，要求输出 JSON 候选；没有 Grok 时使用规则，来源各有区别。系统提示词、输出类别、币名和合约字段都围绕 memecoin trading signals。

候选包含类型、摘要、置信度、引用，以及可选币名和地址。结构化输出有利于后续处理，但不等于事实已核实。截断条目、批量上限和摘要都可能损失细节。

### 3.3 代币解析与去重

通过 DexScreener 根据地址或精确币名选取相应链上的交易对，记录当时价格。去重主要使用任务自己的“代币标识＋信号类型”及 12 小时窗口。

这能抑制同一个币的重复通知，但并不是跨来源事件聚类。通用版需要另外处理别名、规范 URL、内容重复、同一事件和后续进展。

### 3.4 Jev 分流

可选地通过 OpenRouter 的 decisions 接口让 Jev 判断候选是否值得交易者关注。默认低于 15% 的候选过滤，剩余候选按优先级进入较重检查。未配置密钥时这层可关闭。

值班助手是另一个环节：Jev 的选择在置信度达到默认 70% 时可直接采用，不确定信号再交给 Grok。概率、关注价值和事实正确性是不同概念，不能把分值解释为准确率。

### 3.5 安全检查

支持链上已关联代币的信号复用 Instant Crawl：

- 规则识别 DANGER 时过滤。
- 每次最多扫描有限数量，并受总时长预算限制；超预算候选延后。
- 首次扫描失败延后；连续第二次失败无判定放行。
- 无代币或不在支持范围内时，不走同样的完整检查。

因此“所有信号都已安全验证”“骗局绝不会到达用户”超出源码保证。可展示实现，但不能沿用绝对安全表述。

### 3.6 交付

信号进入私有收件箱，可经 Telegram 发给已绑定用户；可选值班 Bot 补充 LOOK / WATCH / AVOID。公共地图可展示任务和状态，并不意味着私有信号全文向所有人共享。

Telegram Bot、Mini App 的实际交付与配置需要另测。MCP 提供外部读取接口，也不意味着助手连接后无需安排调用就能永久自动值守。

### 3.7 反馈

爬虫信号在用户定义窗口内采样价格，使用窗口内峰值判断是否达到涨幅阈值，记录回撤；无价格可标记 unscored。扫描判定另外有 24 小时价格与流动性追踪。

命中规则不是因果证明或收益模拟：没有证明用户能在对应价格成交，也没有扣除手续费和滑点。通用监控更没有统一的“涨了就正确”，需另设评价机制。

## 4. 代币扫描、合约检查与自动发现

Instant Crawl 根据市场、持币分布、增发／冻结权限、关联钱包、创建者历史、同名币等因素加减分，输出 CLEAN、OK、RISKY、DANGER 或 TOO_EARLY。不同链的可用检查不同，数据失败与未知值不能理解为没有风险。

Contract X-Ray 读取 EVM 字节码，识别函数选择器、代理与危险权限，并使用 evmole 辅助分析函数和存储行为；Solana 读取 Token-2022 扩展。网站分析静态读取页面与脚本，结合语法树和模式规则寻找疑似盗取钱包的调用组合，不执行站点代码。

这些是领域专用静态与启发式检查，不能等同正式审计、所有路径可达性证明或真实买卖模拟。

Launch Radar 从第三方新币档案与推广中筛候选，再运行扫描，受候选条件、配额和预算限制。应描述为主动发现来源中的候选，不能宣传成覆盖所有新币或全网数据。

## 5. MCP 与开放接口

固定版本公开五个工具：

- whats_new：查询授权任务的新信号，未变化时可让助手停止后续调用。
- scan_token：运行代币扫描，返回风险分数与因素。
- crawler_signals：读取授权任务信号。
- my_crawlers：读取任务状态、目标、声誉等。
- trending_scans：读取最近扫描。

这些没有创建用户交易、转账或代客买卖工具。MCP 扫描不触发 X 搜索。接口存在凭据、OAuth、任务可见范围与速率限制，但各助手客户端兼容性本次没有实测，README 罗列的客户端名称不能直接当作完整兼容认证。

## 6. 系统架构与维护成本

技术栈为 Next.js、React、TypeScript；前后端、进程状态、任务调度与大量领域逻辑处于同一应用中。任务与信号持久化到本地 JSON 快照，先写临时文件再重命名；默认文件为 .data/state.json。代码存在 db/schema.sql，不代表实际主链路已经使用 Postgres。

重要运行条件：

- 常驻服务：进程停止就停止监控，静态托管只适合本研究展示。
- 可恢复状态：需要游标、任务进度、通知结果和规则版本；读取快照失败后的行为需进一步实测。
- 多实例协调：进程内预算、并发与状态不天然共享；扩大规模需要另外设计。
- 外部服务：来源可能改变结构、限流或不可用；搜索与 AI 依赖密钥及付费。
- 信息保真：摘要应能回到原文，区分发布时间、采集时间和提醒时间。
- 安全获取：公开页面的私网地址阻断、协议／端口限制、跳转校验和大小限制适合通用化后保留。

网页中的成本计算器仅计算 N × 1440 / T × C，其中 N 为任务数、T 为分钟间隔、C 为假设单价。所有输入是可编辑示例，不代表上游报价；也不包含缓存、重试、Token 数、搜索帖子计费或不同来源的成本差异。

## 7. 价值与本质

本研究归纳四种潜在价值：

1. 覆盖：持续观察，减少频繁打开多个平台。
2. 相关性：按用户目标筛选，减少无关阅读。
3. 上下文：将摘要、领域信息和来源放在一起。
4. 反馈：记录提醒以后发生的事，校准任务与规则。

原项目最接近可迁移资产的是“持续观察 → 按偏好判断 → 私有交付 → 后续反馈”。代币提供了统一身份和可自动取样的数字结果，这也掩盖了通用化真正困难的部分：其他领域的对象如何对应、不同报道是否同一事件、何时出现新进展，以及怎样评价提醒是否有用。

相对搜索，它提供持续性；相对普通聚合，它增加按偏好的解释与领域检查；相对单页变化提醒，它尝试同时利用多种来源。但没有证据证明在同等任务下它必然更快、更准或更省钱。

跨平台也不等于事实已被独立验证。三条转发可能来自同一公告，来源数量不能直接当作独立佐证。用户选来源、描述目标和提供反馈仍是系统质量的重要条件。

## 9. 通用化方案：需要保留和替换什么

### 9.1 建议对象

Topic（主题及别名、关注规则）→ Source（平台配置、权限、覆盖和游标）→ RawItem（原文、来源编号、发布时间、采集时间、快照）→ Event（事件与状态进展）＋Evidence（原文关联）→ Notification（用户、触发原因、投递和反馈）。

一个主题可对应多个采集任务；采集层尽量不丢原文。事件关联与来源采集分开，允许人工拆分、合并与纠正。

### 9.2 保留

- X／Telegram／网页来源适配器外壳和增量游标。
- 周期调度、重试、超时、限流与预算思想。
- 安全获取公开网页的限制。
- 私有收件箱、通知通道和 MCP 增量读取思想。
- 规则加可选 AI 的分层处理。

### 9.3 重写

- types.ts、spec.ts：币、链、信号类别、价格结果改成主题、事件和证据。
- analyze.ts：去掉币名强制条件、行情解析和交易提示词；规则路径同样支持普通信息。
- store.ts、auth.ts、http.ts：普通用户身份、主题所有权、访问隔离；不能只删登录页面。
- 去重：来源 ID／规范 URL／哈希先做精确去重，再做对象、时间和语义关联；同主题新事实仍保留。
- 评价：有用／无关、重复、发现延迟、抽样漏报，替代币价命中和积分声誉。
- 持久化：根据规模考虑 SQLite 或共享数据库；增加重启恢复、投递去重、规则版本和失败原因。
- 通知：静默时间、摘要、重要进展、已读和收藏；区分无更新、抓取失败、被过滤、预算耗尽。
- MCP：以主题、事件和变更工具替换代币扫描接口，保持范围受控。

### 9.4 移除或新增

移除链上行情、代币扫描、合约与持币检查、钱包支付、金库回购、销毁、积分市场和治理。保留原来夹在这些模块中的通用安全设施。

RSS、GitHub Releases／Issues 等是建议新增来源，不是原项目已有能力。每个平台都需要确定公开范围、接口或合法接入方式、鉴权、频率和恢复策略。这里没有承诺支持所有平台，也没有给出未经实施的工期估算。

## 10. 第一版路线与验收

1. 领域解耦：建立普通主题与原始条目，让不含币名和地址的内容进入系统。
2. 最小闭环：少量可靠来源、增量采集、存储、原文链接与通知；重启后能继续。
3. 信息质量：精确去重、实体别名、事件关联和进展；同一公告不重复提醒，新日期或结论仍通知。
4. 真实评估：人工标注任务样本，记录误报、重复、发现延迟与已知遗漏；按规模完善后台与数据库。

建议使用的指标包括：相关提醒占比（人工认为相关的提醒／全部提醒）、重复提醒比例、首次发现延迟、采集成功率、投递成功率、用户认为有用的比例。召回率需要预先建立或抽样补齐已知事件集，不能仅凭系统发出的提醒计算。

这些指标是评价方案，本次未执行相应实验。网页示例为固定虚构内容，只解释处理步骤，不构成通用监控后端。

### 15.2 实际用户路径

1. 选择全部 AI、AI 编程、智能体、多模态、模型研究、产品与工具等方向，缩小当前信息范围。
2. 选择综合探索、看 AI 新闻、找产品线索或找开源项目，明确本次目的。
3. 查看来源覆盖并开关来源；通过包含词、排除词、时间、排序和搜索进一步整理已采集的信息。
4. 打开信息详情，阅读匹配原因、原文短摘、来源、时间及仓库字段，跳转原文核实。
5. 收藏值得继续研究的线索，导出研究清单；将方向和规则保存为自定义方案，便于重复使用。

收藏及方向、来源开关等偏好保存在当前浏览器，不提供跨设备同步。自定义关注方案保存领域、目的、包含词和排除词；创建方案不会启动定时任务。导出是用户下载本地清单，不向外部联系人发送内容。

### 15.4 搜索词、方向和过滤如何生效

采集和浏览筛选分为两层。服务器读取固定 RSS，并执行固定 GitHub topic 查询；用户输入的方向、目的和关键词主要用于筛选当前已采集的数据，不会转成全网搜索请求。

方向带有可读词表，例如 AI 编程关联 coding、code、copilot、developer 等词，智能体关联 agent、agentic 等词；方向匹配依赖标题、原文短摘、仓库名和主题标签。目的按新闻、产品线索和仓库类型进一步限制。

包含词可以选择“任意一个命中”或“全部命中”；排除词命中任一个就过滤。逗号、中文逗号和换行可以分隔关键词，忽略大小写；英文词有边界处理，避免短词意外匹配较长英文单词，中文按文本包含。搜索框中的多个空格分隔词要求全部满足。没有同义词扩展、自动翻译或模型语义判断；英文原文中的事实不会因为输入中文意译就自动命中。

过滤过程同时检查来源开关、条目隐藏、内容类型、方向词、包含词、搜索词和时间范围。页面展示匹配原因，相关度由命中的规则词产生可解释排序；分数不是准确率、可靠性评分或产品质量评分。

### 15.5 信息整理与呈现边界

RSS 解析原文标题、作者、原链接和 pubDate；没有发布时间就保存空值，不用采集时间代替发布时间。短摘去掉 HTML 后最多 200 字符，内容来自来源原文；仓库短摘来自 description。没有调用语言模型，没有生成 AI 摘要。

条目保留发布时间、采集时间；仓库还分别保留创建时间、信息更新时间和最后推送时间。仓库创建不是产品首次发布，更新时间也不是 release。星数是采集时总数；语言和许可证字段缺失时保持未知，不能据此推断可商用。

服务器按规范化 URL 的哈希生成稳定 ID，并合并相同 URL；前端对相同 URL 汇总来源。此处只做精确重复合并，没有语义事件聚类、实体别名关联、跨来源独立证据确认或同一事件新进展识别。标题和短摘中的发布、更新等词可能将 RSS 信息标为产品线索，所有这类分类均未代表实际试用。

来源身份与内容可信度分开：官方来源可以说明发布方发布了什么；社区作者、产品自述和仓库描述不自动升级成独立实测结论。每条信息保留原文入口，用户可据此继续核实。

### 15.6 服务、缓存和失败处理

新增采集器使用 Node.js 原生能力，无第三方依赖；每次 HTTP 请求限制 18 秒、2.6 MB 响应，每个 RSS 最多 12 条，GitHub 每组最多 6 条。数据契约与来源细节见 `web/explore/SOURCES.md`。

`GET /api/explore/state` 返回条目、来源状态、最近成功时间和运行日志；`POST /api/explore/refresh` 返回 202 后后台采集，`GET /api/explore/status` 提供运行进度。只允许预设来源 ID，不开放任意抓取接口。来源失败时保留上次结果并标明过期，不能把失败当作“没有更新”；失败也不会覆盖最近成功采集时间。

本地缓存为 `web/.runtime/explore-state.json`，逐来源保存结果，最多保留 20 轮运行记录。随网页交付的初次真实数据保存在 `web/explore/snapshot.json`。默认不自动周期刷新；关闭本地服务后没有持续后台采集。

### 15.8 尚未实现及后续需要验证的价值

已形成“控制范围—筛选—阅读—保留研究线索”的可操作闭环；仍未实现模型分析、语义聚类、事实核查、自动定时监控、通知、账号体系、多用户隔离和跨设备同步。没有把所有来源无限抓取，也没有计算未测量的准确率、召回率或时间节省。

下一步应围绕实际任务人工评估：选定 AI 方向后是否留下有用信息，来源是否漏掉关键更新，关键词是否误杀，是否减少重复阅读，以及收藏是否帮助后续源码研究。取得标注样本后再决定引入模型、事件关联和定时交付，而不是将它们提前写成已有能力。

### 16.2 原库的能力与可复用价值

CrawlHive 把多种来源接入、定期执行、增量读取、规则和可选模型处理、领域检查、去重、保存与私有交付组合成一套面向代币研究的工作流。其价值有两个层次：

- **实现积累**：来源参数、读取路径、游标、内容清理、超时、错误处理和平台特例，减少重新探索接口与采集流程的工作。
- **组合闭环**：采集后继续判断、保存、交付和回看，使用户不必手工把多个工具接成处理链。

这些判断有固定版本的[调度实现](https://github.com/h100envy/crawl-hive/blob/77cfe1c7a42f0d071bee49ac9ebb77fdf0556827/src/lib/server/crawl/scheduler.ts)、[分析主流程](https://github.com/h100envy/crawl-hive/blob/77cfe1c7a42f0d071bee49ac9ebb77fdf0556827/src/lib/server/crawl/analyze.ts)和[持久化实现](https://github.com/h100envy/crawl-hive/blob/77cfe1c7a42f0d071bee49ac9ebb77fdf0556827/src/lib/server/persist.ts)支持；实现存在不等于长期可靠性已经验证。

目前没有充分证据证明它持有难以复制的独家数据、算法或商业壁垒。不能从“公共来源和常见技术”直接推出“只有来源名单”或“没有价值”；稳定接入、可维护性和处理闭环本身就需要工作。另一方面，也不能仅凭功能数量、AI 标签或源码存在，就宣称有独家算法、事实核查能力、长期有效信号或成熟生产服务。

原库中的行情、权限检查、风险扫描与后续价格评价，服务其交易研究用户。它们不适合当前 AI 研究目标，因此可以剥离；本研究没有据此断言币相关能力对原目标用户无用，更没有实测其投资收益。

### 16.3 本质是四个环节，加上持续状态

| 环节 | 实际工作 | 容易混淆的边界 |
| --- | --- | --- |
| 来源控制 | 确定观察对象、平台、账号、频道或网址，记录身份与覆盖 | 选了平台不等于获得全平台、私有内容或完整历史 |
| 信息搜索 | 有查询能力时主动搜索；没有时读取指定来源或比较更新 | 搜索请求、来源订阅和本地已采集内容检索是不同操作 |
| 信息过滤 | 清理、规则匹配、排除、分类、去重与可选模型相关性判断 | 关键词命中不等于语义理解，相关不等于真实或值得购买 |
| 信息呈现 | 保存、摘要或原文短摘、匹配理由、来源链接、时间线和交付 | 展示清晰不等于完成核验，摘要不能取代证据 |

持续状态贯穿四环：记录已经读过什么、游标到哪里、哪次失败、为何留下、后来发生了什么。原库有来源增量和领域去重；本仓库原型有真实来源状态、规范 URL 去重、日志和收藏。通用事件身份、语义聚类和跨平台新进展识别仍未实现，不能把它们写成已确认能力。

### 16.4 我们的思考：从“关注 AI”变成可执行任务

“AI 信息”“AI 产品”“AI 新闻”只是大范围标签，还不足以决定应留下什么。更可操作的配置是 **方向 × 目的 × 条件**：例如“AI 编程 × 找可研究的开源项目 × 优先能本地运行、文档完整、有明确许可证的候选”。

不同目的需要不同结果结构。新闻重点看发生了什么、何时发生和原始公告；产品线索重点看解决的问题、适合谁、可用状态与待试用项；开源项目重点看能力证据、实现方式、运行条件与许可证。作者说法、源码可确认和实际试用应分别标记。

知向目前已经提供方向、目的、来源开关、字面关键词、原文与收藏；“本地可运行”“文档完整”还没有成为经过验证的自动质量判定。产品描述命中一个词不能替代安装运行；仓库有许可证字段也不能替代阅读许可证文本。网页中的未来结果模板是扩展方向，不是假定原型已经理解全部这些条件。

### 16.5 可以扩展什么，以及先后顺序

| 层次 | 当前状态 | 合理扩展 |
| --- | --- | --- |
| 来源与原文 | 4 个公开来源、按需采集、短摘、时间、失败保留旧数据 | 增加指定发布者、GitHub Releases／Issues、更多官方订阅，逐项验证接入 |
| 规则与偏好 | 方向词、类型、包含／排除、时间、排序、自定义方案 | 别名、词组、可解释规则配置和用户“有用／无关”反馈 |
| 事件与变化 | 规范 URL 精确去重，无语义事件层 | 建立项目／产品身份，同一事件关联、进展比较、人工纠正 |
| 分析与交付 | 原文短摘、匹配理由、收藏与导出；无模型、无自动通知 | 在有标注样本后评估模型提取与翻译，再考虑摘要、定时任务和交付 |

扩展目标不是无限增加来源和模型调用。先确认小范围是否能稳定得到与任务有关的信息，保留原文和失败原因；再增加来源、事件层和自动交付。钱包、积分、代币关联、行情和币价命中评价可从本场景移除，但用户身份、权限、预算、持久化和错误处理若进入多用户服务仍需要重新设计。

RSS 和 GitHub 采集器属于本仓库新增，原作的原生监控来源仍是 X、Telegram、Docs 与 DexScreener 四类。原作可选 AI 和通知路径不代表知向已经调用模型或已经发出通知。

### 16.6 个人使用价值：预期收益与评估分开

对当前研究多个 GitHub 项目、理解 AI 产品的个人场景，预期价值是：把关注范围记下来，减少平台切换和同一公告的重复阅读；把零散消息变成有来源、可收藏、能继续研究的线索；在回看时知道当时为何留下和哪些判断仍待验证。

这些是产品假设，尚未取得时间节省或信息质量实验结果。可以用同一组具体任务人工评估：

| 想验证的收益 | 应记录的证据 | 当前不能宣称的结论 |
| --- | --- | --- |
| 少花时间寻找线索 | 手动与使用工作台完成同一任务的时间、实际完成情况 | 已节省某个比例的时间 |
| 留下的信息更相关 | 对保留条目标注有用／无关，记录误杀例子 | 已达到某个准确率或可靠性分数 |
| 关键更新不容易漏掉 | 建立已知事件集，与实际采集覆盖比较 | 仅凭已收到的信息证明召回率高 |
| 减少重复阅读 | 同 URL 重复量、不同链接同事件的人工复核 | 精确 URL 去重已经解决语义重复 |
| 帮助继续研究 | 收藏后进入原文、运行或记录结论的实际转化 | 收藏数量本身代表研究质量 |

相较一次性搜索，持续关注的价值还取决于历史状态和新进展识别；相较通用聊天，研究价值取决于来源覆盖、证据保留和可复查。知向目前是验证个人探索闭环的原型，不是完成了上述对照评估的成熟信息服务。

接入方法和平台名称必须分开记录。同一个平台可能同时提供 RSS、查询 API、指定对象 API 和公开 HTML，各自的权限、覆盖和维护成本不同。

| 方法 | 适合获取什么 | 接入与稳定性需要核对 |
| --- | --- | --- |
| RSS／Atom | 发布者订阅中最近若干文章或更新 | 是否提供日期、摘要、稳定 GUID、分页或历史；常不要求密钥，但不保证完整历史、实时性和永久可用 |
| 查询 API | 平台允许搜索的对象与字段 | 查询语法、排序含义、认证和配额、分页、时间窗口、对象可见性；“搜索结果”不等于完整归档 |
| 指定对象 API | 某仓库、账号或资源的发布与变更 | 读权限、可获取的事件类型、分页和增量游标；对象更新时间不能冒充发布时间 |
| 公开 HTML | 公开频道预览或指定页面文本 | 页面结构、渲染方式、公开范围与变更检测；结构变化可能使解析失效，读不到内容不能算无更新 |

目录每项应保留：平台与具体入口、获取方法、认证限制、覆盖对象及粒度、增量或搜索行为、主要失败与稳定性边界、额度或成本说明、证据链接、核对日期和是否实接。内容相同但链接不同，仍可能需要未来事件关联层；官方入口也不代表所有观点已被独立核实。

成本不能只看“是否有 API key”。至少要区分平台付费与额度、请求频率和流量、本地或服务端运行、可选模型调用，以及接口或 HTML 变化后的维护工作。本仓库四源采集未配置密钥、没有模型费用，不代表所有候选平台免费或长期不限流。候选条目的当前条件以目录所引官方文档为准；“文档可查”不等于已开通账户、获得权限或成功采集。
