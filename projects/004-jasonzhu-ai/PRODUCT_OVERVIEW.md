# 004 产品能力与扩展方向

截至 2026-10-17，004 可以定位为一个**从问题出发、保留来源、积累发现的 AI 研究工作台**。用户提出想研究的问题，系统搜索公开资料、尝试读取原文、分析和筛选候选，再把链接、理解和下一步保存下来。

它帮助个人开发者扩大观察范围，理解陌生领域的具体任务，找到值得研究的开源项目和 AI 产品，并决定下一步该核实什么。当前已经跑通研究与保存流程；候选是否构成产品机会、能否持续节省研究时间，仍需要实际使用和用户验证。

这里的“库”包含三层：网站入口库告诉我们去哪里观察；研究过程记录保存本轮如何查找；发现库保存值得继续研究的材料和判断。当前 004 是可运行的本地应用，没有对外提供通用 SDK。

## 从网站入口研究到产品扩展

本次产品思路来自用户分享的 [X 帖子](https://x.com/shenxiankk/status/2107493081146691700)及围绕其中网站链接的讨论。我们先问这些入口是否有价值、还能去哪里发现需求与优秀产品，再把研究方法逐步做进 004：

1. **评估和补充来源入口：**寻找真实需求、值得研究的 GitHub 项目和实用 AI 产品，扩大个人职业经验以外的观察范围。
2. **形成研究导航：**整理 10 个入口，说明各自适合找什么、怎么搜索，以及不知道搜什么时如何开始。
3. **保存研究发现：**记录链接、自己的理解与下一步，让探索可以继续。
4. **接入自动研究：**将实际使用过的搜索、读原文、分析筛选流程接到网页，由本地 Codex 执行并保存结果。
5. **探索产品方向：**在这个流程之上，研究个人研究助手、工具评估、需求雷达等可能的产品。

这条演进脉络依据本次对话整理。当前 10 个入口包含后续补充，不能整体归为原帖清单；自动研究和发现库属于我们的后续实现。原帖本轮访问返回 403，未重新核实其逐项链接，不补写未经核实的原帖内容。

004 目录更早保存过 JasonZhu.AI 个人网站研究，目录名因此保留。该内容作为历史参考单独保留；当前产品实践的主来源入口为上述 X 帖子，代码由本仓库维护。

## 已有能力与具体产出

| 能力 | 现在能做什么 | 产出或边界 |
| --- | --- | --- |
| 提出研究问题 | 输入方向，选择综合探索、真实需求、GitHub 项目或 AI 产品 | 当前输入上限为 300 字；范围过大时应拆成几个问题 |
| 没有关键词时开始 | 从随便探索、真实问题、开源项目、AI 产品四种方式进入 | 推荐浏览入口与阅读步骤，帮助形成具体问题 |
| 找到观察来源 | 10 个中英文入口，30 条检索模板，说明用途、信号与阅读方法 | 可按语言、类别等筛选，生成 Bing 或 Google 检索式 |
| 执行联网研究 | 调用本机已登录的 Codex，搜索并尝试读取公开页面 | 展示搜索和打开动作、运行状态、来源；支持取消与历史查看 |
| 分析候选 | 整理问题或工具作用、已有办法、个人价值、未知项和下一步 | 属于有来源的研究判断，仍可被后续证据修正 |
| 检查来源条件 | 检查主链接与打开记录的关联，尝试独立读取并匹配短引文 | 记录来源角色及读取状态；来源不满足条件的候选不入库 |
| 保存有价值的发现 | 自动保存或手动选择保存；也能手工记录三类材料 | 保存具体链接、摘录、个人理解、下一步及进展状态 |
| 继续管理研究 | 编辑、关键词与类型/状态筛选、回收站恢复、带入采集计划 | 当前进展为待研究、研究中、已整理、暂缓 |
| 防止重复与覆盖 | 自动入库按记录 ID 和规范化链接去重 | 保留原有个人理解和状态；同一主题的不同链接尚未语义归并 |
| 备份与复用 | JSON 导出与合并导入，Markdown 导出 | JSON 含回收站；Markdown 导出全部未删除记录，方便继续研究 |
| 组织采集计划 | 保存人群、任务、来源、现有办法、观察信号和下一步 | 追加来源、只补空字段；可生成扩展搜索、提取证据、去重筛选指令 |

网页的三个主要操作区域是[自动研究](http://127.0.0.1:4176/1014_codex_project/004-jasonzhu-ai/#research)、[网站入口](http://127.0.0.1:4176/1014_codex_project/004-jasonzhu-ai/#directory)和[发现库](http://127.0.0.1:4176/1014_codex_project/004-jasonzhu-ai/#discoveries)。

## 来源如何帮助理解问题

来源承担不同角色。研究一个方向时，需要把用户经历、现有方案和使用限制放在一起看；不能把所有网页都当成同一种需求证据。

| 来源类型 | 当前入口 | 更适合观察什么 | 理解材料时关注什么 |
| --- | --- | --- | --- |
| 社区经历 | Reddit、V2EX、知乎、小红书、Hacker News | 谁在做什么、卡在哪一步、怎样手工补救 | 亲历者还是提问者；时间、条件、回复和最后采用的办法 |
| 软件使用反馈 | G2、Capterra；GitHub Issues / Discussions | 功能缺口、迁移原因、集成与部署困难 | 人群是否匹配，问题是否已解决，评价是否受激励 |
| 有交付要求的任务 | Upwork | 输入、交付物、重复频率、发布预算 | 发布预算与实际付款分开；一次外包与持续订阅分开 |
| 已有解决方案 | GitHub、Product Hunt；进一步打开产品官网与文档 | 功能、工作流、限制、替代方案 | README 或官网说明与实际运行效果分开 |

GitHub 和 Hacker News 可同时提供问题材料与解决方案，因此分类之间有重叠。官网和官方文档是研究中进一步寻找的原始来源，不计入固定的 10 个导航入口。

**目前的导航入口与自动执行是两条相互配合的路径。** 导航按本地模板生成搜索链接；自动研究根据输入问题和固定研究说明选择公开来源。它没有把页面上选中的入口自动转换成严格的执行白名单，也没有为 10 个网站逐一建立采集接口。部分站点需要登录或存在访问限制，实际可读范围逐次记录。

## 运行原理与数据存放

一次自动研究由网页提交到本地 Node 服务。服务检查输入并启动单个官方 Codex CLI 任务，Codex 使用联网搜索工具寻找资料、打开具体页面，再返回统一结构的来源、候选、排除理由和限制。

程序随后检查候选主链接是否能对应到来源、来源是否有可关联的打开记录，并尝试独立抓取短引文进行匹配。模型负责理解和提出判断；程序负责格式、来源条件、数量上限和去重；用户负责判断是否采用结果以及后续验证。

| 层次 | 负责什么 | 当前保存位置 |
| --- | --- | --- |
| 入口知识 | 网站用途、搜索模板、阅读要点 | 项目的静态数据文件 |
| 执行与分析 | 运行状态、搜索/打开动作、来源和结构化候选 | 本机服务的 `.runtime/auto-research/`；历史选择器展示最近 20 轮 |
| 个人研究 | 发现记录、个人理解、下一步与采集计划 | 当前站点的浏览器存储；可导出备份 |

自动研究只发送本轮方向、目的和研究说明，**不会自动检索或上传已有发现库**。把历史发现带入新的研究、围绕同一主题持续追问、自动整合多轮结论，仍是可扩展能力。现在可以回看历史、手工整理发现并重新提交问题。

当前任务提示模型最多使用 3 组查询、6 个来源，程序最多保留 3 条发现，另有运行超时与动作上限。该设计适合小范围探索；研究大主题时应分轮推进。

来源状态分为“本地匹配到短引文”“有原文打开记录，AI 摘录待独立复核”“只有摘要或不可读”。前两类可作为发现的主来源。短引文匹配只能证明某段文字出现过，打开记录只能证明工具尝试/完成了相应打开动作，都不能单独保证全文读取、作者陈述真实或商业结论成立。

## 对我们有什么实际价值

最直接的价值是把“随便浏览很多网页”变成可继续的研究过程：每轮围绕一个问题找少量具体材料，留下理由、来源与下一步，减少以后重新寻找和重新理解同一材料的工作。跨行业观察可以扩大问题来源，而来源中的具体工作过程帮助我们补足职业经验以外的背景。

对维护多个开源研究项目和网页演示的个人开发者，当前可以这样使用：

| 研究任务 | 示例问题 | 合理的阶段性结果 |
| --- | --- | --- |
| 理解陌生行业 | 小型工作室怎样整理客户零散修改意见？ | 工作步骤、已有办法、反例、需要向实际用户确认的问题 |
| 寻找可借鉴项目 | 什么开源项目能统一收集产品反馈？ | 少量仓库、适用条件、部署与许可待核查项、阅读或试跑计划 |
| 选择 AI 工具 | 哪类工具能把反馈整理为任务？ | 官方能力、使用门槛、替代办法及实际试用的比较方案 |
| 发现产品切口 | 现成工具解决后，哪些步骤仍需手工处理？ | 具体缺口假设、证据和验证动作，而非直接立项结论 |
| 准备做原型 | 应先做哪个最小流程来验证价值？ | 输入与输出、人工基线、目标用户、验收方式 |
| 整理学习与研究 | 哪些项目值得深入，为什么？ | 可找回的研究记录、优先级理由及下一步 |

这些方向的共同条件是：有可阅读的公开材料，问题可以缩小到具体人群和任务，而且下一步能通过阅读、试用或小实验推进。大范围市场规模估计、实时全网监测、私有资料分析、项目自动部署及产品效果验证，需要额外的数据和执行能力。

## 可以扩展的产品

下面按复用当前能力的程度排列。它们是候选产品形态，尚未验证市场需求、价格或收入。

| 产品方向 | 面向谁与交付什么 | 可以复用什么 | 还要补什么 | 最小验证方式 |
| --- | --- | --- | --- | --- |
| 个人研究助手 | 经常探索问题的人；持续维护一个主题的证据与结论 | 搜索、阅读、筛选、发现保存 | 主题工作区、历史材料检索、连续追问、结论版本 | 同一主题连续研究几轮，观察是否减少重复查找 |
| GitHub 项目评估台 | 个人开发者与小团队；比较能否采用或借鉴一个项目 | 仓库发现、已有方案比较、证据记录 | 固定 commit、许可与依赖核查、隔离运行、维护状态、试跑报告 | 用同一任务试跑两个项目，比较安装成本与实际完成情况 |
| AI 工具选型台 | 独立开发者与具体岗位；选择适合自身任务的工具 | 产品发现、官方资料阅读、价值与限制分析 | 同一输入的试用对比、质量标准、成本记录、适用条件 | 用一组真实脱敏任务对照人工办法与候选工具 |
| 需求雷达 | 寻找选题的开发者与产品人员；追踪重复出现的问题 | 社区来源、问题理解、排除理由 | 定时采集、跨来源主题归并、独立样本计数、趋势与反例 | 固定一个窄主题，观察新材料是否改变原有判断 |
| 垂直行业或竞品情报 | 对某领域持续决策的人；获得有出处的变化摘要 | 公开资料读取、来源保留、研究历史 | 固定监测对象、增量比较、过期检查、变更提醒 | 跟踪少量对象，检查每条更新能否影响实际决策 |
| 团队研究知识库 | 小团队；共享材料、判断与尚未解决的问题 | 结构化发现、状态、导入导出 | 服务端存储、账户权限、协作评论、冲突与版本处理 | 让几位真实使用者共同维护一个研究主题 |
| 用户反馈整理产品 | 已有产品用户的开发者；把零散反馈整理为待处理事项 | 原文与理解分离、分类、下一步和状态 | 接入获授权的自有反馈、主题归并、人工确认、任务流与反馈闭环 | 用一批脱敏真实反馈比较漏项、误合并和整理时间 |
| 证据关联的 PRD 助手 | 准备开发产品的人；将发现整理为可验证的需求说明 | 来源、已有办法、未知项、下一步 | 需求与来源关联、验收条件、实验记录、验证结果回写 | 写一份最小需求说明，检查每个关键主张是否有依据或被标为假设 |
| 研究简报或专题报告服务 | 需要研究结论但不想操作工具的人；按题获取精选材料 | 检索流程、筛选理由、导出能力 | 固定质量标准、人工审阅、交付模板、反馈与更新 | 先交付少量人工审阅报告，观察读者是否继续采用 |
| 研究能力接口 | 其他工作流或应用；按任务调用研究并接收结构化结果 | 本地执行链路、统一输出结构、来源检查 | 任务队列、认证、配额、错误恢复、服务化执行与成本管理 | 先接入一个内部实际流程，验证稳定性与成本 |

对当前阶段，个人研究助手、GitHub 评估和 AI 工具选型最接近已有流程；定时雷达、团队协作和反馈管理需要新增较多数据与运行能力。这是实现距离判断，不代表它们的商业价值排序。

可以形成两条发展路线：一条深化研究本身，让查找、比较、积累和更新更可靠；另一条围绕研究中反复出现的具体任务开发独立工具。研究工作台可以支持后者的选题和验证，但不能替代实际用户采用的证据。

## 当前证据与后续衡量方式

已有验证包括三轮网页自动研究和一条更早的手工记录。2026-10-17 的导出快照共 5 条发现：2 条需求线索、2 条 GitHub 项目、1 条 AI 产品。其中 Fider、ClearFlask、Canny Autopilot 是研究候选，尚未部署或试用。一次候选因主来源缺少可关联的打开记录而被排除，之后通过收窄任务、逐页打开补充研究，说明目前仍需要人在异常和证据不足时调整研究。

既有自动研究实现通过了 39 项测试，并做过真实网页执行、刷新恢复、入库去重及导出检查。这证明了已检查范围内的流程可以运行；尚未测量长期节省的时间、真实用户复用率或付费意愿。当前实测运行中，独立抓取未成功完成短引文核对，不能把工具打开与模型摘录描述为独立事实核验。

后续判断产品价值，可以围绕以下问题记录实际数据：

- **结果是否可信：**关键判断能否回到正确原文；多少来源不可读；是否混淆作者宣传、用户经历和我们的推断。
- **发现是否有用：**保存之后是否真的继续阅读、试用、联系已获授权的参与者或开展实验；排除是否有合理理由。
- **是否减少工作：**与普通搜索、通用 AI 加笔记的做法相比，完成同一研究任务的耗时与返工是否减少。
- **积累是否有效：**隔一段时间能否找回材料、理解当时判断，并用新证据更新结论。
- **成本是否可接受：**一次研究的耗时、模型用量、失败与补查次数，是否值得换取最终可用的发现。

如果进一步做成多人在线产品，还需要解决账户、同步、权限、执行环境、配额与成本控制。目前自动研究依赖本地 Node 服务和 Codex 登录；静态网页托管只能提供导航、样本、计划与浏览器发现库，不能独立执行自动研究。
