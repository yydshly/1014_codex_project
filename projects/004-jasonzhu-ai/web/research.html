01 / 核心理解

让研究有来源，也有后续。

能力
找资料、读原文、分析筛选，沉淀三类发现与后续动作。
原理
问题决定检索方向；公开来源提供材料；模型帮助理解；程序检查来源条件；人决定如何验证和采用。
价值
扩大观察范围，减少重复查找和重新理解，让每次探索都能接着做。节省时间的程度需要用真实任务测量。
产品目标
帮助个人开发者从“想研究什么”走到“依据是什么、下一步做什么”，逐步积累自己的研究资产。
扩展空间
可深化为个人研究助手、项目与工具评估台，再扩展到需求雷达、行业情报、团队知识库和反馈处理。

03 / 工作原理

用来源约束判断，用下一步推动研究。

  1. 1

    提出一个具体问题

    描述人群、任务和想获得的结果；选择需求、GitHub、AI 产品或综合探索。

  2. 2

    搜索，再尝试读取原文

    网页提交到本地 Node 服务，再由已登录的 Codex 搜索公开网络、打开具体页面，记录查询和来源。

  3. 3

    分析材料，检查来源条件

    模型整理作用、价值、已有办法和未知项；程序关联主链接与打开记录，尝试独立匹配短引文，保留排除理由。

  4. 4

    保存值得继续研究的发现

    每轮最多保留 3 条；自动保存按 ID 与规范化链接去重，不覆盖个人理解、状态或已移入回收站的记录。

  5. 5

    由人补采与验证

    回读、试用、访谈和小实验后，决定采用、做原型、继续研究或暂缓；形成新问题后再次提交。

什么证据，支持什么判断？

用户经历提供问题线索；官方文档说明功能；真正的使用效果需要试用与观察。来源分为短引文已匹配、有打开记录但摘录待复核、只有摘要或不可读。

打开记录与引文匹配不能单独证明内容真实，也不能推出市场规模或付费意愿。

数据在哪里？

入口知识随页面发布，运行历史保存在本机服务目录，发现与计划保存在当前站点的浏览器中。更换浏览器或从本地切到公网，需要通过 JSON 备份迁移。

新研究只发送本轮方向和目的，不会自动检索或上传已有发现库。

04 / 信息来源

按问题选择材料，而不是只追踪热度。

社区经历

Reddit · V2EX · 知乎 · 小红书 · Hacker News

看具体人群怎么做事、哪里卡住、怎样补救。读正文、回复和后续，区分亲历、提问与推广。

软件反馈

G2 · Capterra · GitHub Issues / Discussions

看使用障碍、迁移原因和部署问题；核对条件、修复状态与评价来源。

有交付要求的任务

Upwork

看输入、结果、验收与重复频率。发布预算与实际付款需要分开理解。

已有解决方案

GitHub · Product Hunt · 产品官方资料

从仓库和发布页找到方案，再回 README、文档与官网核实功能和限制。

部分来源需要登录或存在访问限制，实际可读范围逐次记录。GitHub 与 Hacker News 跨类别出现，官方资料是进一步查找的原始页面，不额外计入 10 个入口。查看逐站方法与访问记录 ↗

05 / 价值与产品目标

先帮助研究者做出一个更有依据的决定。

当前最贴近我们的使用场景，是维护多个开源研究项目与网页演示：跳出自身职业经验，发现任务，比较方案，留下可以继续推进的判断。

理解陌生工作

例如“工作室怎样整理客户修改意见？”产出工作步骤、手工补救和需要继续问的问题。

寻找开源与 AI 工具

例如“哪些项目能统一收集反馈？”产出少量候选、适用条件和阅读、安装或试用计划。

准备产品选题

观察现成工具之后还剩哪些手工步骤，形成缺口假设、反例与最小验证动作。

积累自己的研究库

保留当时的依据、理解与下一步，隔一段时间仍能找回，并根据新证据调整结论。

目标：从“我看到一个有趣的东西”，推进到“它解决谁的什么任务、为什么值得我继续研究、下一步如何验证”。

这些方向适合有公开材料、可缩小到具体任务的探索。实时全网监测、大范围市场估计、私有资料分析与自动部署，仍需要额外能力。

06 / 可扩展产品 · 构想

复用研究流程，面向不同的后续任务。

以下按实现距离分组；每个方向仍需验证实际需求。现在最接近的是个人研究助手、GitHub 评估台与 AI 工具选型台。

从现有流程继续深化

个人研究助手

维护一个主题的证据与结论。

需补：主题工作区、历史检索、连续追问、结论版本。

GitHub 项目评估台

判断一个项目能否采用或借鉴。

需补：固定版本、许可与依赖检查、隔离运行、试跑报告。

AI 工具选型台

比较具体任务下的工具表现。

需补：统一试用输入、质量标准、成本记录与人工基线。

增加持续跟踪与多人协作

需求雷达

追踪重复出现的问题与反例。

需补：定时采集、主题归并、独立样本计数、趋势变化。

垂直行业或竞品情报

获得有出处的变化摘要。

需补：固定对象、增量比较、过期检查和更新提醒。

团队研究知识库

共享材料、判断与待解决问题。

需补：服务端同步、账户权限、评论、冲突与版本处理。

把研究结果接到实际工作

用户反馈整理

将零散反馈转为待处理事项。

需补：获授权的自有反馈接入、人工确认、任务与反馈闭环。

证据关联 PRD

把发现转成可验证的需求说明。

需补：主张与来源关联、验收条件、实验结果回写。

研究简报服务

按题交付精选材料与结论。

需补：质量标准、人工审阅、交付模板和持续反馈。

研究能力接口

让其他流程接收结构化研究结果。

需补：任务队列、认证配额、错误恢复与成本管理。

另一条路线是根据反复出现的真实任务开发独立工具。研究工作台可以支持选题与验证，具体工具仍需实际用户采用的证据。完整说明含各方向的最小验证方式 ↗

Fider、ClearFlask 与 Canny Autopilot 已作为研究候选保存，并补查官方资料；尚未部署或试用。曾有候选因缺少可关联的打开记录而未入库，之后通过收窄问题、逐页打开补充研究。

下一阶段怎样判断是否值得继续？

  • 关键判断能否回到正确原文，是否区分经历、宣传与推断。
  • 保存后是否真的继续阅读、试用或做实验。
  • 与普通搜索、通用 AI 加笔记相比，研究耗时与返工是否减少。
  • 积累的记录是否容易找回、理解和更新。
  • 运行成本、失败与补查次数，是否值得换取最终可用的发现。
