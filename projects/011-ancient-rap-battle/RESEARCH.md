## 定位与价值

这个项目把一次历史人物对唱，组织成“内容设定 → 音乐与定妆 → 逐句镜头 → 审核 → 剪辑与包装”。Claude Code 按 `SKILL.md` 调度步骤，用户选歌、制图和验收；Python 脚本处理文件、调用视频 API 并组装成片。它没有训练自己的音乐、图像或视频模型。[流程手册](https://github.com/10291124jcjc-dotcom/ancient-rap-battle/blob/e5e40fa3612777133a141c8448122dd0fd45e4cc/SKILL.md)

最有借鉴价值的是制作经验如何落入工程约束：同一角色共用参考图；歌词单句对应短素材；用观众、对手反应和 DJ 镜头形成节奏；把歌词时间、素材版本、偏移量和剪辑表分别保存。这样，改一句歌词或更换一个镜头时，有机会只重做对应环节。

适合借鉴的场景包括系列化娱乐短片、角色对话、歌词短视频和围绕固定格式的内容生产。涉及准确知识讲解时，还要补充史料核查：示例有意将正史与演义作为创作对立面，艺术梗不能直接当作历史结论。

| 价值 | 对应机制 | 实际边界 |
| --- | --- | --- |
| 减少重复准备 | 共用角色设定、提示词、参考图和镜头模板 | 仍要筛选歌曲、图片和镜头 |
| 让返工更便宜 | 一句一条、多个 take、独立剪辑表 | 重做会增加生成费；跨镜头人物一致性仍靠约束和人工选片 |
| 让过程可检查 | 分镜表、逐句听写检查、任务日志、预览 | 没有完整的生产任务平台或审核后台 |
| 保留局部恢复能力 | 已选 take 可复用，缺片能用占位画面预览 | 不是完善的持久化任务恢复；远端超时仍需人工处理 |
| 统一成片风格 | 景别、站位、道具、字幕、调色规则 | 不保证模型逐条服从提示词 |

## 实现分析

### 从设定到时间轴

`episode.json` 汇总标题、时代、角色名字、服装、声线描述、半音变调值、道具、双方歌词及逐句动作。`common.py` 约定目录、参考图名字和字体位置。它们组成一整期内容的输入约定。[示例配置](https://github.com/10291124jcjc-dotcom/ancient-rap-battle/blob/e5e40fa3612777133a141c8448122dd0fd45e4cc/examples/zhouyu-vs-zhugeliang/episode.json)、[公共模块](https://github.com/10291124jcjc-dotcom/ancient-rap-battle/blob/e5e40fa3612777133a141c8448122dd0fd45e4cc/scripts/common.py)

`analyze_song.py` 先用 Demucs 拆出人声和伴奏，再用 faster-whisper 生成带时间的识别结果。文字识别用于定位，字幕正文仍取预先给定的歌词。伴奏的起音强度用于寻找节拍，第一轮 BPM 搜索是 `70 ≤ BPM < 120`，随后局部细化。脚本通过两段歌词前几句与识别文本的相似程度找到段落锚点，再按“一句约一小节、每小节四拍”建立后续时间。

按小节裁剪歌曲后，脚本分别对两段人声变调，再与伴奏混合，输出音乐、独立人声、逐句时间和字幕。这个策略要求歌曲节奏和歌词分段比较规则；自由速度、复杂换拍、拖长或漏唱都可能破坏假设，必须核对打印的 `line check` 和实际听感。[音频分析源码](https://github.com/10291124jcjc-dotcom/ancient-rap-battle/blob/e5e40fa3612777133a141c8448122dd0fd45e4cc/scripts/analyze_song.py)

### 从逐句时间到素材和剪辑表

`make_clips.py` 依据每句开始、结束时间及角色动作，拼接参考图说明、景别、运镜、人物站位、声音要求和场景规则，生成 `clips.json` 与 `edl.json`。近景优先使用半身裁图，避免全身参考把镜头引向远景。参考图、明确道具和站位规则是软约束，不是身份锁定技术。

默认 A 16 句、B 18 句：A 的 4、5、6、12 句和 B 的 7、8、13 句用过场镜头覆盖，因此实际需要 27 条说唱素材。另有 OPEN、CROWD、B_REACT、LAUGH、A_REACT、DJ、CHANT、END 八条过场。CROWD 为 10 秒，其余素材为 5 秒，总计 35 条、180 秒待生成素材；成片按 EDL 取片段，因此比原始素材总时长短。[分镜生成源码](https://github.com/10291124jcjc-dotcom/ancient-rap-battle/blob/e5e40fa3612777133a141c8448122dd0fd45e4cc/scripts/make_clips.py)、[分镜说明](https://github.com/10291124jcjc-dotcom/ancient-rap-battle/blob/e5e40fa3612777133a141c8448122dd0fd45e4cc/references/shot-template.md)

### 从素材请求到候选镜头

`h3run.py` 从素材清单切出单句独立人声，将文字、参考图片和参考音频提交给 MiniMax H3。它会缓存相同文件的上传结果，记录远端任务编号，轮询完成状态，下载为 `clips/<id>_t<n>.mp4`。生成任务可以并行执行；单条失败不会直接中止其他任务。

每个候选版本执行自动音频检查，通过后记录到 `picks.json`；检测到音轨起点偏迟时，写入 `shifts.json`。`--all` 只为还没有已选版本的素材提交请求。脚本保存了任务日志，但没有提供完整的未完成任务恢复命令，也没有严格的远端任务去重保证。网络中断或轮询超时后，应先用日志里的 task ID 核对远端状态，避免直接重跑产生重复费用。[生成脚本](https://github.com/10291124jcjc-dotcom/ancient-rap-battle/blob/e5e40fa3612777133a141c8448122dd0fd45e4cc/scripts/h3run.py)

### 自动质检的准确含义

`qa.py` 从生成视频抽取音轨，再与提交的人声比较约 10 毫秒尺度的对数能量包络。它搜索音频起始偏移、计算整体和短窗口相关性，尝试发现重唱、明显漂移或延迟。它没有分析视频里的嘴部，也没有逐个音素比对，因此“通过”仅代表音轨形态较接近，并不能证明嘴形准确、人物正确或画面自然。[音频检查源码](https://github.com/10291124jcjc-dotcom/ancient-rap-battle/blob/e5e40fa3612777133a141c8448122dd0fd45e4cc/scripts/qa.py)

`lipcheck.py` 是可选辅助工具：用 MediaPipe 人脸关键点估计嘴部开合程度，将其与人声音量变化做相关性搜索，报告可能的时间差。代码按最大人脸作为说唱者；双人镜头、侧脸、麦克风遮挡或嘴部过小会影响判断。它也没有证明口型内容与音素吻合。移动画面后必须重新人工试看。[嘴部检查源码](https://github.com/10291124jcjc-dotcom/ancient-rap-battle/blob/e5e40fa3612777133a141c8448122dd0fd45e4cc/scripts/lipcheck.py)、[作者踩坑记录](https://github.com/10291124jcjc-dotcom/ancient-rap-battle/blob/e5e40fa3612777133a141c8448122dd0fd45e4cc/references/pitfalls.md)

### 剪辑与包装

`assemble.py` 读取素材清单、EDL、选片与偏移量，按统一音乐时间轴拼接画面。缺失素材显示深灰占位，便于在素材未齐时检查节奏。说唱素材不足时保留最后一帧，避免提前移动整段破坏声音对应。反应和观众镜头可以用来覆盖不理想的片段。[草稿组装源码](https://github.com/10291124jcjc-dotcom/ancient-rap-battle/blob/e5e40fa3612777133a141c8448122dd0fd45e4cc/scripts/assemble.py)

`package.py` 用 Pillow 画透明字幕、标题和名字卡，再用 FFmpeg 叠图、轻调色、混入过场现场声并输出成片及手机预览。默认生成是 768P，包装尺寸是 1920×1080，这是输出放大。`cover.py` 从选定镜头抽帧，生成竖版 3:4 与横版 16:9 封面。[包装源码](https://github.com/10291124jcjc-dotcom/ancient-rap-battle/blob/e5e40fa3612777133a141c8448122dd0fd45e4cc/scripts/package.py)、[封面源码](https://github.com/10291124jcjc-dotcom/ancient-rap-battle/blob/e5e40fa3612777133a141c8448122dd0fd45e4cc/scripts/cover.py)

## 进一步拆解：规则、算法与状态如何配合

### Skill 承担流程协议，文件承担状态交接

`SKILL.md` 告诉 Claude 何时创作、何时运行哪个命令、生成什么文件、在何处展示给人确认。它承担的是自然语言流程协议。Python 侧没有一个包办全部阶段的主程序：分析歌曲、建分镜、调用 API、组装和包装分别执行，通过本地目录和文件传递结果。

因此，流程里的“自动”有不同层次：音频处理是确定的本地程序；视频生成是脚本调度外部概率模型；写词和发布文案由 Claude 按规则创作；选歌、制图、预算和验收由人推进。网页任务队列、可视化审核和完全无人值守的生产调度不在原版实现之内。[操作协议](https://github.com/10291124jcjc-dotcom/ancient-rap-battle/blob/e5e40fa3612777133a141c8448122dd0fd45e4cc/SKILL.md)

### 歌词定位依靠锚点和网格，不是逐字强制对齐

节拍函数先处理伴奏的频谱变化，以正向变化强调起音；尝试多个 BPM 和起始相位，让规则拍点尽量落在强起音处。第一轮步长为 0.1 BPM，局部细化步长为 0.01 BPM。它找到的是一个贯穿歌曲的规则网格，不会自动处理每段任意变化的速度。

段落定位只保留汉字，拿已知前四句与识别结果的候选窗口进行 `SequenceMatcher` 匹配；匹配分数低于 0.25 则退出。找到起始位置后，先吸附到节拍锚点，再用四拍一小节逐句推进。在每个预计小节内选择识别到的首字时间，字幕正文取已知歌词，并对上一句尾字跨小节的情况作简单跳过处理。这解释了为何同音字错误有时不妨碍定位，也解释了漏唱、重复唱、换拍和跨小节长句为何需要人修正。[音频算法](https://github.com/10291124jcjc-dotcom/ancient-rap-battle/blob/e5e40fa3612777133a141c8448122dd0fd45e4cc/scripts/analyze_song.py)

### 素材清单与剪辑表是两个不同的契约

素材清单解决“生成什么”：角色、镜头 ID、提示词、图片、人声取段、生成时长，以及开头是否留静音。剪辑表解决“在成片何时播放哪条素材、从素材哪里取”。同一条观众或反应素材可以在不同位置取不同片段，不必每次重新生成。B 的第一句另留 0.5 秒举麦时间，音频与 EDL 都要考虑这个前导。

下面仅是说明字段关系的示意，时间不是原作测量结果，也不是可直接运行的完整配置：

```json
{
  "clip": {
    "id": "A01",
    "kind": "rap",
    "dur": 5,
    "lead": 0,
    "audio": [4.92, 7.5],
    "images": ["人物半身参考.png", "表情参考.png", "场地.png"],
    "prompt": "这一句的景别、动作、人物与声音规则"
  },
  "edit": {
    "t0": 4.92,
    "t1": 7.5,
    "clip": "A01",
    "in": null
  }
}
```

`in: null` 表示按人声起点与前导自动对齐；过场镜头的数字 `in` 表示固定从素材的某个秒数取片。`picks.json` 再把素材 ID 指向具体 take，EDL 不需要因为重抽而整体重写。这个分离是局部替换和成本控制的基础。[分镜数据生成](https://github.com/10291124jcjc-dotcom/ancient-rap-battle/blob/e5e40fa3612777133a141c8448122dd0fd45e4cc/scripts/make_clips.py)

### API 调用保存了结果，但还不是持久任务系统

生成请求携带文字、`reference_image` 和说唱镜头的 `reference_audio`。提交后记录 task ID，每 15 秒查询一次，轮询超过 30 分钟退出。批量模式最多 10 个工作线程，相邻提交间隔 8 秒。上游保留任务、素材候选和用量记录，能让人追查某一条发生了什么。

选片逻辑也有明确限制：第一条自动检查通过的候选可写入 `picks`；如果已有选片，随后重抽通过也不会自动覆盖它。要换成新版本，需要明确修改选片。`--all` 根据是否已有选片决定跳过，未进一步核对其素材是否仍存在或输入是否变化。超时后也没有读取旧 task ID 自动续查的完整入口，直接重跑可能再次提交付费任务。[请求、轮询和选片](https://github.com/10291124jcjc-dotcom/ancient-rap-battle/blob/e5e40fa3612777133a141c8448122dd0fd45e4cc/scripts/h3run.py)

### 音频检查阈值与视觉检查的差别

`qa.py` 把音轨重采样为 8 kHz 单声道，以 80 个采样点计算一组对数 RMS，得到约每 10 毫秒一个值的音量包络。先找整体相关性最高的偏移，再以约 1 秒窗口、0.5 秒间隔检查局部变化。整体阈值为 0.85，局部低于 0.9 时记录首次漂移位置；接受还要求有效段长度达到代码中的时长条件，最长要求至约 2.3 秒处。它不是要求五秒画面的每一帧都准确。

还有一个值得记录的实现差异：注释写偏移搜索从 -0.2 到 +0.6 秒，但实际循环跳过了所有负值，因此有效搜索只有 0 到 +0.6 秒。该工具偏向查找生成音轨晚起的情况，不能按注释理解为双向修正。即使音轨保持一致，也可能出现嘴部错误，因为它没有读取任何视频像素。[音频检查条件](https://github.com/10291124jcjc-dotcom/ancient-rap-battle/blob/e5e40fa3612777133a141c8448122dd0fd45e4cc/scripts/qa.py)

`lipcheck.py` 才会读取画面：每帧以嘴部两关键点距离除以脸高，估计相对开合，再与人声音量作相关性搜索。它固定按 24 fps 计算时间，挑最大脸作为说唱者；没有验证音素，也没有自动判断谁实际在唱。结果只打印出来，不会自动写入偏移文件。这里的“视觉检查”仍然是启发式测量，不能替代人看。[嘴部检查计算](https://github.com/10291124jcjc-dotcom/ancient-rap-battle/blob/e5e40fa3612777133a141c8448122dd0fd45e4cc/scripts/lipcheck.py)

### 偏移为什么改变画面，而保持总歌曲不动

组装阶段统一使用 `music_final.wav`，不会把每条生成镜头的唱声直接拼成总音乐。镜头音轨主要用于之前的筛查。对 `in: null` 的说唱素材，组装脚本依据 EDL 起点、人声切片起点、前导静音和 `shifts` 计算源片入点。

例如某素材从第 0.20 秒才开始跟随输入人声，确认后记录正偏移 0.20；组装时多裁掉源画面开头的 0.20 秒，相当于把后面的画面提前，歌曲仍停留在原时间轴。若画面因此不足，末帧定格补齐，避免为补长度而挪动整条镜头。对不唱歌的反应镜头则可以调整固定入点，编辑自由度更大。[画面偏移与定格](https://github.com/10291124jcjc-dotcom/ancient-rap-battle/blob/e5e40fa3612777133a141c8448122dd0fd45e4cc/scripts/assemble.py)

| 已有基础 | 固定版本的局限 | 类似系统的改进方向 |

## 原版复现步骤

以下是固定版本的操作指南，本研究没有执行付费生成。`EP` 代表一期内容的工作目录。建议在上游独立目录或隔离环境中操作。

1. 下载上游并固定版本；准备 Python 3.9+、带 rubberband 的 FFmpeg、Suno / Midjourney 账号和可用 MiniMax API 凭据。Python 包包括 `demucs faster-whisper soundfile scipy numpy pillow`，可选嘴部检查另需 `mediapipe opencv-python`。安装后执行 `setup_check.py`。若希望 Claude Code 自动发现 Skill，可将仓库放在 `~/.claude/skills/ancient-rap-battle`，Windows 对应用户目录下的 `.claude/skills/ancient-rap-battle`。[环境检查源码](https://github.com/10291124jcjc-dotcom/ancient-rap-battle/blob/e5e40fa3612777133a141c8448122dd0fd45e4cc/scripts/setup_check.py)
2. 复制示例 `episode.json` 到独立的 `EP`，修改人物、歌词和动作；首轮沿用 16 + 18 句结构，先确认歌词和典故。不要直接修改示例目录混放多期素材。
3. 按 `references/suno.md` 准备三栏提示词，在 Suno 生成并选歌，保存为 `EP/song.mp3`。执行歌曲分析，逐句听核查后再继续。
4. 按 `references/midjourney.md` 准备 8 张图，按约定名字放到 `EP/refs/`。检查脸、服装、配色和道具，再生成分镜表。
5. 查看分镜、检查引用图片；先做估算和请求格式检查。`--estimate` 使用脚本内静态价格，也要求素材清单和引用图片已准备好。`--dry-run` 不提交网络生成，但说唱镜头仍会在本地切音频。
6. 人工确认费用后，先生成一条，查看声音、口型、脸和动作。小样满意才扩大范围；失败时先调整偏移、换版本或切反应镜头，再考虑付费重抽。
7. 组装草稿并审核，确定后包装和导出封面；实际发布前检查平台要求和素材授权。外部服务的使用与商用条件需查当前官方条款。

cd ancient-rap-battle-upstream

# 下列 EP 替换为已备好配置、歌曲和参考图的一期目录

## 先做 3–4 句最小验证

建议先验证约 10–20 秒内容：双方各 1–2 句、少量近景与一个反应镜头。目标是确认“参考图 + 单句人声”是否能稳定得到可接受素材，避免先投入完整一期。

但原版 `make_clips.py` 的镜头位置、过场和封面默认取帧都围绕 16 + 18 句设计。直接把歌词改成 3 句，不应被理解为已具备完善的短片模板。有两条路线：

| 路线 | 做法 | 适合验证什么 |
| --- | --- | --- |
| 尽量沿用原版 | 保留完整设定和时间轴，只选 `A01 A02 B01 B02` 估算并生成；用局部预览分别看这些位置 | API、参考图、人声跟随和单句质量 |
| 构建独立短实验 | 制作短音频，人工核对句界；独立创建短 `clips.json` / `edl.json`，或修改模板及封面、包装中的固定位置假设 | 从短歌曲到连续小成片的完整闭环 |

原版路线可以先运行 `h3run.py EP A01 A02 B01 B02 --estimate`；审核价格后才去掉 `--estimate`。`assemble.py` 的 `--from` / `--to` 可限制预览区间。若需要连续的 3–4 句短片，应该走第二条路线。

小样的人工验收至少看：指定歌词是否被保留、主要音节与嘴部变化是否协调、角色和道具有无跳变、机位是否符合预期、切镜是否顺畅、重做费用是否可接受。记录每个候选版本和失败原因；自动相关性数值作为辅助证据。

## 如何实现类似系统

下面是基于源码的设计建议，不是上游已实现的完整平台。先把核心闭环做通，再扩展成批量生产。

### 按阶段构建

| 阶段 | 最小可交付内容 | 建议保留的审核点 |
| --- | --- | --- |
| 1. 内容计划 | 角色、短歌词、动作、参考图和来源 | 内容是否成立、是否具备使用权限 |
| 2. 音频与时间 | 总音乐、独立人声、逐句起止；不规则歌曲允许手工改时间 | 听逐句切片，避免靠错误句界继续生成 |
| 3. 镜头计划 | 每条素材的参考、提示词、时长及剪辑位置 | 预算、镜头可读性和人物一致性 |
| 4. 生成适配器 | 上传、提交、查询、下载，提供商细节封装在模块内 | 第一条小样，通过后才批量 |
| 5. 检查与选片 | 音频检查结果、视觉问题标签、候选列表 | 人工选择接受、修正或重做 |
| 6. 后期输出 | 对齐音乐的草稿、字幕、包装、封面 | 成片试听、字幕、素材来源和发布声明 |

音乐、图片、视频均可通过适配器替换；替换前要验证新服务能否接受输入人声、参考图数量、时长、分辨率及同步控制。只支持图生视频的服务不一定能直接复现音频跟随效果。提示词可以约束结果，但不能代替服务真实的输入能力。

### 建议的数据契约

- **内容层**：`episode_id`、`schema_version`、角色稳定 ID、歌词行 ID、来源与授权备注；角色名字改变不应导致旧素材混用。
- **时间层**：统一秒为单位；每句 `start < end`；保存原始音频哈希和时间修订历史，允许人工覆盖自动对齐。
- **素材层**：每条素材固定 ID，记录 `kind`、角色 / 歌词行引用、提示词版本、图片和音频哈希、生成时长；EDL 只引用稳定素材 ID。
- **任务层**：记录提供商、模型、参数、任务 ID、输入哈希、提交时间、状态、请求费用估算与实际回传用量。凭据单独从安全配置读取。
- **审核层**：take、检查结果、人审决定、偏移量和问题原因分开存储；接受的是特定候选版本，不只是一个布尔值。
- **交付层**：记录所选版本、EDL 版本、输出参数、文件哈希；修改字幕或水印可只重跑后期。

### 失败恢复与费用

建议任务采用 `planned → submitted → polling → downloaded → checked → accepted/rejected` 状态，并将状态在每个阶段持久化。重启后先查询已有 task ID，再决定是否新建任务。以输入哈希判断“请求是否相同”，在服务支持时使用幂等键。网络错误可以受控重试；内容被拒、余额不足或参数错误需要分别处理。

缓存也必须有失效规则。原版分离和 ASR 的缓存主要依赖文件是否存在；如果在同一目录替换歌曲，旧结果可能被复用。类似系统应把输入哈希、工具版本和参数加入缓存键。角色或提示词改变时，也要标记受影响素材，不能只检查是否已有选片。

费用建议按**生成秒数**估算，另外列出重试预算、音乐与制图账号费用、人工筛选时间。审批应绑定具体素材范围与额度；超额或重抽再次确认。页面内计算器只能做假设分析，不应默默触发真实付费任务。

上游代码的 768P 常量为 `$0.08/秒`，默认 180 秒推导得到 `$14.40`；作者另记录示例实际约 `$16`。二者分别是静态基础估算与特定历史样例，均不保证现价，也未覆盖其他服务和所有重试。[历史计价常量](https://github.com/10291124jcjc-dotcom/ancient-rap-battle/blob/e5e40fa3612777133a141c8448122dd0fd45e4cc/scripts/h3run.py)
