00 / WHAT WE UNDERSTAND

从它能做什么，到我们为何研究它。

把源库事实、我们的推导和仍待验证的产品假设放在同一条主线上。

01 / 源库效果 · 固定源码核读

部署后，拥有一个自己的聊天空间。

EdgeChat 交付完整的聊天应用与部署方案。成员通过网页、PWA 或 Android 入口进行群聊、私信、发文件与录音；网页支持一对一实时语音，并能按限定范围桥接 Telegram 群和其他 EdgeChat 实例。

查看已有能力与边界 →
02 / 底层原理 · 固定源码核读

界面、权限、实时协调和持久化各有职责。

Vue 提供界面，Workers + Hono 处理请求与权限，Durable Objects 协调房间和连接；D1、KV、R2 分别保存业务数据、登录会话和附件。消息先保存再广播，断线后补取历史；实时语音通过 WebRTC 直连或 TURN，信令走后端。

展开架构与消息旅程 →
03 / 引发的思考 · 我们的判断

通信、使用入口与互联，是三个不同问题。

群聊和单聊回答“怎样交流”，网页和客户端回答“从哪里使用”，桥接和工具接口回答“与谁连接”。完整应用不等于一键嵌入 SDK；能增加一个聊天框或 AI 入口，也不代表形成了有优势的产品。

04 / 对我们的价值与意义 · 我们的判断

留下可复查的架构知识和一个候选工程起点。

它帮助我们理解实时通信、存储、桥接、授权与信任边界。在确有独立部署需求时，可评估复用现有链路；是否省事仍取决于改造、运维、平台成本及许可证要求。研究的意义也包括更有依据地决定何时采用成熟方案。

05 / 可扩展产品 · 尚未验证的假设

让交流贴近某个业务问题，才有继续开发的理由。

候选方向有客户交付协作室、页面反馈与问题处理、Telegram 社区支持台、AI 任务协作室、通用嵌入式聊天 SDK，以及多人音视频。前四类需补齐业务状态、分工和闭环；后两类需大量组件、媒体与运营工程。均需另行验证需求。

06 / 当前取舍 · 随新证据调整

保留研究，暂不主动开发通用聊天产品。

成熟聊天、客服和 SDK 已提供不少基础能力。我们先等真实项目出现明确痛点，再比较现成服务、简单表单与二次开发，通过小范围试用验证收益。本次发布的是研究展示网页；上游聊天后端、桥接、通话、性能和需求付费尚未实测。

06 / TRUST & AGENTS

两个容易误读的关键词。

「加密」要看密钥在哪里，「AI」要看谁负责智能。

服务端静态加密

数据写入前加密，
服务端仍能解密。

消息明文→Worker 加密→D1 / R2 密文

新正文和新附件使用 AES-256-GCM，密钥以版本管理。读取时由 Worker 验权后解密，因此部署者与运行环境仍在信任范围内。

继续看加密边界 ＋
  • 历史明文兼容读取，不会自动批量补加密。
  • 文件名等元数据不代表全部加密。
  • 后台没有正文查看入口，不等于部署者技术上无法读取。
  • 轮换时旧密钥仍需保留，旧数据依赖它解密。
这里提供的隐私模型是服务端加密，不能视为端到端加密。

07 / WHY IT MATTERS

值得研究的，是这些取舍。

从功能往后看，是运维、连接与信任关系的重新分工。

以下为研究判断
01

减少机器维护，
保留运营责任。

把长连接、数据库和文件交给托管服务，让小团队更容易拥有独立入口。与此同时，密钥、备份、账号治理和平台配额仍需要有人负责。

02

连接已有习惯，
降低迁移阻力。

桥接的价值是让人继续使用各自熟悉的入口。代价是副本进入外部系统，同步范围、失败恢复与隐私边界都必须说清楚。

03

把应用变成工具，
让 AI 参与协作。

WebMCP 把页面里的操作表达成结构化入口，展示了 AI 使用现有应用的一种方式。真正的智能行为，仍取决于接入的模型与授权方式。

当前阶段的取舍

保留研究，暂不开发通用聊天产品。

固定版本包含完整聊天应用的代码与部署方案，具有潜在工程复用、自部署和学习价值。但在已有成熟聊天、客服与 SDK 产品的情况下，仅组合现有聊天功能，商业差异化有限。先有具体的未满足需求，再决定是否使用这个项目。

网页模块是可开发方向

封装成可嵌入组件，需要把三层接好。

完整聊天网站可以被二次开发成网页浮窗、页面讨论区或私信组件；当前不能视为已提供任意网站一键接入的通用 SDK。

界面封装

把聊天室拆成可嵌入的组件，适配页面尺寸和交互。

身份与会话

对接网站账号，把用户、业务对象与允许访问的会话对应起来。

接口与后端

封装收发、上传和重连；消息存储与实时转发仍由后端承担。

网站页面→聊天组件→会话与权限→EdgeChat 后端
六个扩展方向

能开发，还要看是否值得投入。

以下是基于现有基础的产品假设，不是上游现成功能，也不是已证实的需求或付费机会。切换方向查看使用者、缺口和判断。

工程价值

有明确需求时，减少重复开发。

已有接口、消息与存储链路可作为改造起点。是否更省事，还要与现成组件、简单表单等方案比较。

自部署与研究价值

独立运行、理解和修改完整系统。

适合需要独立实例与 Telegram 群互联的人，也适合研究 Cloudflare 实时通信和系统分工。

商业产品价值

通用功能的差异化有限。

需要明确谁因为什么问题愿意使用、迁移或付费。更多聊天种类与接上模型，本身不能证明产品优势。

成熟产品，已经覆盖了不少基础能力。

以下参考此前查看的官方产品说明，用于说明现成选择；不是本轮实测性能比较，也不作为市场需求已被验证的证据。

继续投入的前提

某个真实项目出现具体痛点，现成方案不能合适地解决，再用小范围试用检查回复耗时、问题解决率或记录复用是否改善。在此之前，保留本轮研究，不主动推进通用聊天模块或新产品开发；这项取舍可以随新证据重新评估。
